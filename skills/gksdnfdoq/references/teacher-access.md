# 교사용 URL 접근과 선택적 화면 진입용 비밀번호

교사 화면이 있는 Apps Script 웹앱을 인터뷰하거나 구현할 때 읽는다. 이 경로에서는 수업·업무 용도와 Firebase 사용 여부에 관계없이 교사 접근에 적용한다. 사용자가 명시한 다른 방식은 우선한다.

## 기본값: 교사용 URL로 바로 사용

- 교사용 접속 URL을 열면 별도 비밀번호나 계정 로그인 없이 해당 웹앱의 교사 기능을 사용하도록 한다. 학생 화면과 교사 화면이 분리된 앱은 URL 분기로 각각의 접속 주소를 제공한다. 예: `?page=teacher`, `?page=student`.
- 수업용 화면 분리 앱은 명렬에서 구성한 학년·반 드롭다운이 교사의 첫 화면이다. 다른 앱은 인터뷰에서 정한 교사 시작 화면을 사용한다.
- 이 방식은 교사용 URL에 접속한 사람에게 교사 기능을 제공한다는 뜻이다. 별도의 신원 확인이 완료된 것으로 기록하지 않는다. 이를 이유로 기본값을 거부하거나 Google 로그인·승인 계정 등록·비밀번호를 자동 추가하지 않는다.
- 여기서 교사 화면은 앱의 결과 조회·활동 관리 등 기획한 기능을 표시하는 화면이다. Firebase 교사 역할이나 프로젝트 관리 권한을 방문자에게 발급하는 절차는 없다.

## 인터뷰에서 화면 진입용 비밀번호를 선택하는 경우

일반적인 앱 사용 흐름에서 교사 화면에 들어가기 전에 비밀번호를 거치고 싶은지 필요한 경우에만 확인한다. 이미 선택한 경우에는 다시 묻지 않는다. 예:

> 교사용 주소를 열면 바로 교사 화면이 나오게 할까요, 아니면 화면 진입용 비밀번호를 먼저 입력하게 할까요? 이 비밀번호는 앱 화면에 들어오는 순서를 제어하며, Firebase 활동 데이터 자체의 읽기를 제한하지는 않아요. 혹은 원하시는 화면 흐름을 편하게 설명해주셔도 좋아요.

- 비밀번호는 **교사 화면 진입용으로만** 사용한다. 이를 데이터 비밀 보호나 검증된 교사 신원·Firebase 권한으로 설명하지 않는다. 사용자가 데이터 자체의 비공개 접근을 별도로 요구하면 화면용 비밀번호만으로 충족했다고 보고하지 않고, 그 요구에 필요한 별도 설계를 확인한다.
- 모든 앱에 비밀번호 질문을 추가하거나 민감한 정보라는 이유만으로 자동 적용하지 않는다. 선택하지 않은 상태에서는 URL 기본 접근을 유지한다.
- 비밀번호의 저장 위치는 `설정` 탭 A1로 정해져 있으므로 다시 선택하게 하지 않는다.
- 중간 요약에는 “교사용 URL로 바로 사용 — 기본 적용” 또는 “교사 화면 진입용 비밀번호 — 설정!A1 대조”와 화면 순서를 기록한다. 비밀번호 자체는 대화 메모·로그·사용 설명서에 넣지 않는다.

## 비밀번호 화면과 시트 기준

화면 진입용 비밀번호를 선택한 앱의 흐름은 다음과 같다.

`교사용 URL → 비밀번호 입력 화면 → 서버에서 설정!A1과 대조 → 일치하면 원래 교사 화면`

수업용 화면 분리 앱의 원래 교사 화면은 학년·반 드롭다운이다. 일반적인 UI 흐름에서는 비밀번호 확인 전 활동 화면·관리 버튼을 표시하지 않는다. 이것을 Firebase 데이터 접근 차단으로 표현하지 않는다.

1. 연결된 Google 스프레드시트에서 정확히 `설정`이라는 탭의 **A1 셀 값**을 교사 비밀번호로 사용한다. 이 셀에 헤더를 넣지 않는다. 기존 탭의 A1이나 다른 셀을 임의로 덮어쓰지 않는다.
2. 입력값과 저장값을 서버에서 문자열로 비교한다. 앞뒤 공백·대소문자를 임의로 바꾸거나 부분 일치로 통과시키지 않는다. 앞자리 0 등이 필요한 비밀번호는 셀에 일반 텍스트로 저장하도록 안내한다.
3. 일치하면 성공 결과를 반환하고 교사 화면으로 이동한다. 틀리면 비밀번호 화면에 머무르며 다시 입력하도록 안내한다. 이 성공 결과로 Firebase 교사 역할·권한표·커스텀 클레임을 발급하지 않는다.
4. `설정` 탭이 없으면 [웹앱 시작 시 초기화](spreadsheet-lifecycle.md)에서 기존 자료를 보존하며 탭을 준비하고 A1에 비밀번호를 설정하도록 안내한다. A1이 비어 있거나 공백뿐이면 화면 진입용 비밀번호가 미설정인 상태로 처리한다. 빈 비밀번호로 통과시키거나 임의의 기본 비밀번호를 사용하지 않는다.
5. 비밀번호를 HTML·JavaScript·URL·공개 설정 객체에 포함하지 않는다. 브라우저에는 성공·실패와 필요한 화면 상태만 전달한다. 시트의 비밀번호를 가져와 브라우저에서 비교하지 않는다.
6. 화면 진입 상태는 데이터 읽기·쓰기 권한의 증명으로 사용하지 않는다. 비밀번호를 바꾸면 다음 진입 확인에 새 값을 사용한다. 학생 자신의 기록인지 확인하는 서버 검증과 데이터 변경 규칙은 별도로 유지한다.

## Firebase를 사용하는 앱과의 연결

Firebase 익명 인증은 두 방식 모두 뒤에서 자동 처리한다. 교사에게 Firebase용 로그인 화면을 추가하지 않는다. **별도의 Firebase 교사 권한 발급 절차는 생략한다.**

- 화면 반영에 필요한 활동 데이터 경로는 Firebase 익명 인증 사용자에게 읽기를 허용한다. 앱은 정한 화면에만 내용을 표시하지만, 비밀번호를 통과하지 않은 접속자도 Firebase 규칙이 허용한 데이터를 직접 읽을 수 있는 구성임을 문서에 정확히 표시한다. 명렬 전체·비밀번호·불필요한 과거 기록까지 RTDB에 공개하지 않는다.
- 화면용 비밀번호를 선택하면 앱은 통과 후 활동 화면과 그 화면의 리스너를 시작한다. 이 실행 순서 자체는 Firebase의 읽기 권한 조건이 아니다.
- 교사 역할용 커스텀 클레임, UID별 교사 권한표, 교사 권한 발급·갱신·회수 API를 기본 구성에 추가하지 않는다. 교사 역할을 부여하려고 배포 계정의 OAuth 호출이나 별도 서버를 새로 구성하지 않는다. 일반적인 Firebase 프로젝트 관리·규칙 배포는 기존 절차대로 수행한다.
- 읽기 허용과 쓰기 허용은 분리한다. [Firebase 규칙](firebase-provisioning.md)에 따라 학생은 자신의 기록만 생성·수정·삭제할 수 있게 하고, 기존 기록의 소유자를 바꾸거나 다른 학생의 기록을 덮어쓰지 못하게 한다. `page=teacher`나 클라이언트의 역할 값, 화면용 비밀번호 통과 여부를 학생 기록의 소유권 검사 예외로 쓰지 않는다.
- Firebase 규칙의 학생 기록 소유권 검사와 Apps Script의 시트 변경 권한 검사는 유지한다. 교사 권한 발급 생략을 데이터 쓰기 전체 허용으로 해석하지 않는다.

## 사용자 점검 안내

[사용자 점검 체크리스트](delivery-and-checklist.md)에 선택한 방식의 기대 결과를 반영한다. AI가 직접 접속·비밀번호 입력·권한 테스트를 수행하지 않는다.

- URL 기본 접근: 교사용 주소로 바로 원래 교사 화면을 사용하며 추가 로그인 질문이 나오지 않는지 사용자가 확인한다.
- 화면 진입용 비밀번호: 첫 화면이 비밀번호 입력이고 `설정!A1`과 일치할 때만 활동 화면으로 이동하는지, 누락·불일치·빈 설정에서는 이동하지 않는지 사용자가 확인한다.
- Firebase가 있으면 화면 흐름에 따른 실시간 표시와 학생 기록의 소유권 제한을 점검 항목으로 제공한다. 활동 데이터 읽기를 비밀번호로 차단하는 테스트는 이 구성의 기대 결과로 넣지 않는다.
