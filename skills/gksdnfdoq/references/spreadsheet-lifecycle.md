# 스프레드시트 자동 연결과 시작 시 초기화

Apps Script 웹앱 경로에서만 적용한다. 이 경로는 사용자가 Google Sheets에서 **확장 프로그램 → Apps Script**로 연 시트 종속형 프로젝트를 사용한다. 별도 시트 ID 입력이나 새 스프레드시트 생성을 기본 절차로 추가하지 않는다.

## 부모 시트 자동 연결

1. 클론한 프로젝트의 실제 스크립트 ID를 기준으로 부모 시트를 식별한다. 사용 가능한 인증된 Apps Script API의 `projects.get` 메타데이터에 `parentId`가 있으면 이를 사용한다. 스크립트 ID·배포 ID를 시트 ID로 사용하지 않는다.
2. 이미 해당 앱의 연결 정보가 저장되어 있으면 부모 정보와 대조해 재사용한다. 다른 프로젝트에서 복사된 시트 ID로 사용자 데이터를 쓰지 않는다.
3. 자동으로 얻은 부모 시트 ID를 초기 연결 코드에 반영해 첫 실행에서 `PropertiesService.getScriptProperties()`에 저장하도록 한다. 사용자가 ID를 소스 코드에 붙여 넣지 않게 한다. 이후 웹앱 서버 처리는 저장된 ID로 `SpreadsheetApp.openById()`를 사용한다.
4. 부모 ID 조회가 지원되지 않거나 필요한 접근이 없으면 시트 문맥에서 실행하는 초기 연결 함수를 제공한다. 이 함수는 `SpreadsheetApp.getActiveSpreadsheet()`로 부모 시트를 얻어 ID를 저장한다. `onOpen()`에는 “웹앱 설정 → 초기 연결” 메뉴를 추가하고 사용자가 한 번 실행하도록 안내할 수 있다. 필요한 실제 Google 권한 승인은 사용자가 완료한다.
5. 웹앱의 `doGet(e)`나 API 실행에서 `getActiveSpreadsheet()`가 항상 동작한다고 가정하지 않는다. 연결 정보가 아직 없으면 원인을 알리는 화면과 필요한 초기 연결 방법을 제공한다. 임의의 시트에 연결하거나 연결되지 않은 상태에서 성공으로 처리하지 않는다.

부모 메타데이터 조회와 연결 정보 준비는 실제 구현에 필요한 작업이다. 앱 테스트를 대신 수행하기 위해 시트 데이터를 추가·수정하지 않는다.

## 웹앱이 열릴 때 실행할 초기화

- `doGet(e)`로 요청 화면의 기본 HTML을 제공하고, 화면 시작 시 `google.script.run` 등을 통해 서버 초기화 함수를 한 번 호출하는 흐름으로 구성할 수 있다. 전역 스피너에 준비 중임을 표시하고, 초기화가 완료된 뒤 해당 화면의 데이터 작업을 이어간다.
- 초기화는 페이지를 열 때 필요한 탭과 헤더의 존재를 확인하고 없는 부분만 준비한다. 재접속 시에도 이미 있는 항목은 건너뛴다. 타이머나 폴링으로 반복 실행하지 않는다.
- 여러 학생이 동시에 처음 접속해도 중복 생성하지 않도록 `LockService.getScriptLock()` 등으로 초기화 작업을 보호하고, 잠금을 얻은 뒤 존재 여부를 다시 확인한다. 종료·오류 경로에서 잠금을 해제한다.
- 초기화의 성공·실패를 모두 처리한다. 실패하면 스피너를 종료하고 커스텀 안내를 표시하며, 필요한 초기화가 끝난 것처럼 데이터 처리를 계속하지 않는다.
- 서버에서 실행할 스키마는 앱 코드가 정한다. 브라우저가 전달한 임의의 탭 이름·헤더로 시트를 만들거나 기존 구조를 바꾸게 하지 않는다.

## 없는 항목만 생성하고 기존 데이터 보존

앱 기능과 [데이터 저장 기본값](data-storage-and-actions.md)에 맞는 탭 이름·필수 헤더·열 매핑을 AI가 설계한다. 최종 입력값과 보관할 활동 내용은 모두 시트에 저장하고, 기록 ID·버전·중복 작업 판단에 필요한 정보도 앱에 맞게 준비한다. 교사에게 기술적인 표 구조를 직접 설계하도록 요구하지 않는다.

| 현재 상태 | 초기화 동작 |
| --- | --- |
| 필요한 탭이 없음 | 해당 탭과 필요한 헤더만 생성 |
| 탭과 필요한 헤더가 있음 | 해당 항목은 건너뛰고 기존 데이터 사용 |
| 탭은 있고 필요한 헤더만 없음 | 기존 데이터 의미를 바꾸지 않는 빈 셀·안전한 새 열에만 보완 |
| 예상 헤더 위치에 다른 값이 있거나 데이터 해석이 불분명함 | 덮어쓰기·재배치하지 않고 충돌한 탭·항목을 안내 |

- 초기화에 `clear()`, `clearContents()`, 기존 탭 삭제·재생성, 기존 행 일괄 교체를 사용하지 않는다. 기존 값·수식·서식·사용자 추가 열을 보존한다.
- 헤더가 이미 있으면 같은 이름의 헤더를 다시 만들지 않는다. 기존 헤더 위치를 사용하는 앱은 실제 위치에 맞는 열 매핑을 유지한다. 고정 위치가 정해진 명렬처럼 다른 위치를 허용하지 않는 경우에는 임의로 열을 이동하지 않는다.
- 누락된 헤더를 보완하더라도 기존 값 위에 쓰거나, 원래 다른 의미의 데이터가 있던 열을 새 필드로 취급하지 않는다. 안전하게 추가할 수 없는 경우 안내하고 중단한다.
- 학생 목록·응답·비밀번호 같은 실제 데이터를 초기화 과정에서 예시 값으로 채우지 않는다. 필요한 빈 구조를 만드는 것과 사용자 데이터를 입력하는 것을 구분한다.

## 이미 정해진 탭의 예외

- **명렬:** 학생 로그인·학급 목록에 필요할 때 준비한다. 탭이 없으면 생성하고 A1 `학번`, B1 `이름`을 준비한다. 2행부터는 사용자가 실제 학생 데이터를 입력한다. 기존 A1·B1 또는 데이터가 충돌하면 보존하고 안내한다. 명렬 데이터가 없으면 로그인 통과나 임의의 학급 목록을 만들지 않는다.
- **설정:** 교사 화면 진입용 비밀번호를 선택한 경우에 준비한다. A1은 비밀번호 값 자체를 저장하는 칸이므로 “비밀번호” 같은 헤더를 넣지 않는다. 새 탭의 A1은 비워두고 설정 필요 상태로 안내하며, 이미 있는 비밀번호를 덮어쓰지 않는다.
- **firebase:** 현재 자동 설정 방식에서는 이 탭을 새로 만들지 않는다. 기존 탭이 있다면 보존한다.
- **기타 앱 데이터 탭:** 인터뷰로 정한 기능에 필요한 탭·헤더만 준비한다. 사용하지 않는 기능의 탭을 미리 추가하지 않는다.

시트 생성·보존 결과는 사용자가 [점검 체크리스트](delivery-and-checklist.md)에 따라 확인한다. AI가 이를 확인하기 위해 웹앱에 접속하거나 실제 데이터를 넣는 테스트는 하지 않는다.
