# 데스크톱 프로그램과 로컬 도구 제작

사용자가 EXE·데스크톱 프로그램·로컬 실행 도구를 원하거나, 다른 프로그램 위에 뜨는 창·바탕화면 상주 등 운영체제 동작이 핵심이라 이 경로를 선택했을 때 읽는다. 일반 웹페이지 안에서 움직이는 요소를 운영체제 위에 떠 있는 프로그램의 완성품으로 대신하지 않는다.

## 실행 환경과 핵심 동작 확인

- 먼저 들은 목적과 실행 요구를 재사용한다. 운영체제와 대상 기기, 개인 사용인지 다른 선생님에게 전달할 것인지, 꼭 필요한 동작 중 미정인 것만 한 번에 1~2개 확인한다. Windows나 EXE를 이미 명시했다면 운영체제를 다시 묻지 않는다.
- 사용자가 기술 이름을 고르게 하기보다 실제 행동으로 질문한다. 예: “다른 프로그램 위에도 계속 보이게 할까요, 필요할 때 창을 열어 쓰면 될까요? 혹은 원하시는 사용 모습을 설명해주셔도 좋아요.” 이미 말한 동작은 다시 선택하게 하지 않는다.
- 상주 도구는 드래그·크기 조절·숨기기·종료 등 실제 사용에 필요한 동작을 목적에 맞게 정한다. 파일 처리 도구는 대상 파일·선택 방법·결과 저장 위치·기존 파일 보존 방식을 파악한다. 해당하지 않는 항목을 필수 설문으로 만들지 않는다.
- 시작프로그램 등록·항상 관리자 권한 실행·서비스 설치 같은 운영체제 변경은 상주 기능과 구분한다. 사용자가 요청했거나 필요한 이유를 설명하고 합의한 기능만 구현한다.
- 이 경로에서는 스크립트 ID·clasp·Google 로그인·스프레드시트·명렬 로그인·Firebase를 기본 준비 항목으로 요구하지 않는다. 별도로 요청한 데이터 연동만 실제 필요에 맞게 추가한다.

## 프로젝트 준비와 구현

1. 기존 프로젝트가 있다면 파일·기술 구성·사용자 변경을 읽고 재사용한다. 새 프로젝트라면 작업 폴더를 준비하고 목적·실행 형태·대상 운영체제·다음 할 일을 `개발진행기록.md`에 남긴다. 스크립트 ID 자리를 미정으로 남겨 나중에 입력하게 하지 않는다.
2. 현재 환경에서 사용할 수 있는 언어·UI 기술·컴파일 및 패키징 도구를 확인한다. 대상 운영체제와 핵심 동작을 지원하는 기술을 선택하며, 이미 정한 기술이 있으면 우선한다. 특정 프레임워크를 모든 도구에 강제하지 않는다. 필요한 명령·지원 범위는 현재 공식 문서와 도움말로 확인한다.
3. [아이디어 인터뷰](idea-interview.md)와 [디자인 지침](design-and-feedback.md)으로 MVP를 만들 만큼만 구체화하고 실제 소스를 작성한다. 화면이 없는 간단한 로컬 도구에는 불필요한 UI를 추가하지 않는다.
4. 저장할 내용이 있다면 목적에 맞는 로컬 파일·설정·데이터베이스 등을 사용한다. 위치와 형식을 기록하고 기존 자료를 보존한다. 수정·삭제·덮어쓰기처럼 영향을 주는 동작은 사용자가 이해할 수 있게 구현한다. Apps Script 경로의 “모든 최종 기록은 시트” 규칙을 이 경로에 옮기지 않는다.
5. 화면이 있는 도구에는 이모지 없는 아이콘·도형, 디자인에 맞는 알림과 주요 비동기 작업의 진행 표시를 적용한다. 웹 기술을 쓰지 않는 프로그램에 HTML·CSS 사용 자체를 강제하지 않는다.

예를 들어 **“Windows에서 다른 프로그램 위에 둥둥 떠 있는 펫”**은 Windows용 실행 프로그램 경로로 다룬다. 다른 창 위에 표시하는 동작, 이동·숨김·종료 등을 지원하는 구현을 준비한다. 단순히 브라우저 안에 그림을 띄운 뒤 같은 요구를 충족했다고 보고하지 않는다.

## 실제 빌드·패키징과 전달

- 핵심 기능을 구현한 뒤 선택한 기술의 컴파일·빌드·패키징 명령을 실제로 수행한다. 실행 결과와 생성된 파일을 확인하고, README에 재현 가능한 빌드 방법을 남긴다. 명령 안내만 출력한 것을 빌드 완료라고 하지 않는다.
- 사용자가 실행 프로그램을 요청했다면 가능한 환경에서 실제 실행 파일·설치 파일·포터블 폴더 등 사용할 산출물을 만든다. 대상 운영체제·아키텍처와 전달 형식을 표시한다. 단일 EXE인지, 함께 있어야 하는 파일·폴더가 있는지 정확히 구분한다.
- 지원 파일·이미지·설정 등 실행에 필요한 자료를 함께 묶는다. 파일 하나만 떼어 실행할 수 없는 구성을 단일 파일 프로그램으로 설명하지 않는다. 개발용 소스와 배포용 결과물의 위치를 구분한다.
- 대상 운영체제용 빌드 도구가 없거나 현재 환경에서 해당 패키징이 지원되지 않는다면, 가능한 소스·설정·빌드 절차를 준비하고 남은 환경과 작업을 명시한다. 다른 플랫폼에서 만든 결과나 아직 없는 파일을 요청한 실행 파일로 제시하지 않는다.
- 업데이트는 프로그램 코드와 사용자 저장 자료의 위치를 구분해 제공한다. 새 빌드로 바꾸면서 사용자 기록을 초기화하거나 기존 작업 파일을 덮어쓰지 않는다.
- 결과물은 사용자가 바로 찾을 수 있는 실제 파일·폴더의 클릭 가능한 링크로 전달한다. 로컬 프로그램에 웹 배포 URL을 만들어내거나, 별도 요청 없이 배포 사이트·공개 저장소 업로드를 추가하지 않는다.
- 진행 기록은 개발 폴더에 보관하고 배포용 묶음에 넣지 않는다. 비밀번호·개인 API 키·로그인 자격 증명을 실행 파일이나 함께 배포하는 설정에 넣지 않는다.

## 한국어 사용 설명서와 사용자 점검

- `README.md`에는 지원 운영체제, 필요한 실행 환경, 어느 파일을 실행하는지, 설치형·포터블 사용 순서, 주요 동작, 숨기기·종료, 데이터·설정 위치, 업데이트, 문제 해결, 변경 이력을 실제 구현에 맞게 적는다. 개발자용 빌드 방법과 선생님의 일반 사용법을 구분한다.
- 코드나 기능을 바꿀 때 같은 작업에서 README와 `개발진행기록.md`도 갱신한다. 기록에는 선택한 기술·빌드 명령·산출물 경로·확인된 실행 결과·남은 작업을 남긴다.
- **앱 동작 점검은 사용자가 한다.** AI는 EXE·GUI 앱을 실행하거나 실제 사용자 파일을 처리해 시험하지 않는다. 컴파일·빌드·패키징 명령의 성공 확인과 실제 앱 실행 검증을 구분하고, 자동 테스트·동작 검증을 별도 추가하지 않는다.
- 사용자가 확인할 목록은 해당 도구의 실제 동작과 기대 결과로 작성한다. 펫이라면 실행·다른 창 위 표시·이동·숨기기·종료를, 파일 처리 도구라면 사용자가 준비한 시험용 복사본으로 파일 선택·결과 저장·원본 보존을 확인하게 안내한다. 모든 목록을 모든 도구에 넣지 않는다.
- “실행 파일 생성 완료 / 사용자 실행 점검 전”처럼 상태를 정확히 보고한다. 변경 파일과 목적, 산출물 링크, 실행 순서, README·진행 기록 위치, 체크리스트를 전달하고 사용자 피드백으로 보완한다.

중간 질문·재개·중단은 [공통 대화 흐름](conversation-continuity.md)을 그대로 따른다. 사용자가 중단했다면 새 빌드·패키징을 시작하지 않고 현재 상태를 저장한다.
