# Firebase 자동 설정·익명 인증·보안 규칙

자동 반영을 선택하고 Firebase 관리 도구·계정·프로젝트 준비가 끝났을 때 읽는다. 이 문서는 Firebase를 실제 사용하는 웹앱의 구현 절차다. 스킬 자체의 문구를 편집하는 요청만으로 원격 프로젝트를 만들거나 설정을 배포하지 않는다.

## 자동으로 수행할 범위

AI가 웹 앱 등록, Realtime Database 준비, SDK 설정 조회와 코드 연결, 익명 인증 활성화, 앱에 맞는 규칙 작성·배포를 수행한다. 설정 안내나 JSON 출력만 하고 작업을 끝내지 않는다. 가능한 MCP 도구를 우선 사용하고, 기능이 부족하면 현재 버전에서 지원하는 CLI를 사용한다. 도구 이름·인자·명령은 실제 제공 기능과 공식 문서로 확인한다. 동작 점검·규칙 테스트는 [사용자 점검 안내](delivery-and-checklist.md)로 제공하며 AI가 직접 실행하지 않는다.

- 새 프로젝트 사용과 익명 인증은 정해진 기본값이다. 같은 결정을 반복해서 질문하지 않는다. 로그인·접근 권한 등 실제로 사용자의 조치가 필요한 단계만 안내한다.
- 원래 프롬프트의 `firebase` 시트 탭 생성, A1 또는 A열에 SDK 초기화 코드 붙여 넣기, 붙여 넣은 코드 파싱은 이 자동 설정 흐름으로 대체한다. 해당 설정 탭을 새로 만들거나 수동 입력을 요구하지 않는다. 기존 탭이 있더라도 사용자 데이터를 삭제하지 않는다.
- 웹앱에는 여전히 Firebase 설정과 SDK 초기화 코드가 필요하다. 이를 AI가 구성한다. 관리 도구의 Google 계정 로그인은 웹앱 이용자의 Firebase 인증을 대신하지 않는다.
- **서비스 계정 JSON·관리자 비공개 키·CLI 로그인 토큰을 Apps Script에 넣도록 요구하지 않는다.** 소스·HTML·시트뿐 아니라 스크립트 속성·사용자 속성·문서 속성에도 저장하지 않으며, AI가 대신 삽입하는 방식으로 우회하지 않는다. Git·로그·사용 설명서에도 기록하지 않는다. 프로젝트 관리에는 로그인된 CLI·MCP 등 관리 도구의 인증을 이용하고, 권한이 부족하면 필요한 권한·연결 조치를 안내한다. 공개 웹 SDK 설정을 스크립트 속성에 저장하는 것은 이 비공개 관리 자격 증명의 저장과 구분한다.
- Realtime Database를 사용하며 Cloud Firestore로 바꾸지 않는다. 웹앱 실행 위치는 Apps Script로 유지한다. 설정 과정에서 Hosting이나 다른 서비스를 불필요하게 추가하지 않는다.
- [시트 저장과 실시간 반영 기본값](data-storage-and-actions.md)을 적용한다. 최종 입력값·활동 기록의 보관과 기준 데이터는 시트에 두고, RTDB에는 실시간 화면 반영에 필요한 최소 상태·임시 복사본만 둔다. 보관할 기록은 버튼에서 시트에 반영한 뒤 필요한 RTDB 갱신으로 이어간다. 시트에 보관하지 않는 실시간 상태는 브라우저 SDK와 RTDB가 직접 통신하며 Apps Script로 중계하지 않는다. 리스너가 시트 기록을 다시 만들지 않게 한다.

## 프로젝트 리소스와 설정 준비

1. 작업 폴더·대상 프로젝트 ID를 대조한다. 같은 앱에 이미 등록된 웹 앱과 데이터베이스가 있으면 확인해 재사용한다.
2. 웹 앱을 등록하고 Realtime Database 인스턴스를 준비한다. 로컬 설정 파일 생성과 원격 인스턴스 생성을 구분하며, 실제 인스턴스 ID·위치·URL을 확인한다. 생성 초기에는 읽기·쓰기가 모두 거부되는 규칙을 사용하고, 앱별 규칙이 완성되면 교체한다.
3. 웹 앱의 SDK 설정을 관리 도구로 가져온다. 예를 들어 현재 MCP에 `firebase_get_sdk_config`가 있으면 등록한 앱 ID로 조회한다. RTDB 생성 후 `databaseURL`이 실제 대상과 일치하는지 확인하고, 빠진 값은 원격 설정을 다시 조회해 채운다. 프로젝트 ID만 보고 URL을 추측하지 않는다.
4. SDK의 공개 설정은 **Apps Script의 스크립트 속성(Script Properties)**에 `FIREBASE_WEB_CONFIG` 같은 전용 키의 JSON 문자열로 저장한다. 아래의 실행 시 설정 로딩을 구현하고, 속성 저장·갱신도 AI가 가능한 Apps Script 관리·실행 수단으로 수행한다. Firebase 관리 도구만으로 Apps Script 속성까지 쓸 수 있다고 가정하지 않는다. 실제 권한 승인이나 초기 설정 함수 실행에 사용자의 조치가 필요할 때만 그 단계를 안내하며, SDK 설정을 수동 복사하는 과제로 넘기지 않는다. 이 설정에는 공개 웹 SDK 필드만 넣고, 위의 비공개 관리 자격 증명 저장 금지 규칙을 적용한다.
5. Firebase Authentication의 Anonymous 제공자를 활성화하는 설정을 작성한다. 현재 MCP의 `firebase_init`이 `auth.providers.anonymous`를 지원하면 이용할 수 있다. CLI 경로에서는 `firebase.json`의 `auth.providers.anonymous`를 `true`로 구성한다. 아래는 새 프로젝트에 필요한 최소 구성의 예이며, 기존 파일이 있으면 해당 항목만 병합한다.

   ```json
   {
     "auth": {
       "providers": { "anonymous": true }
     },
     "database": {
       "rules": "database.rules.json"
     }
   }
   ```

로컬 설정만 작성하고 익명 인증이 활성화됐다고 보고하지 않는다. 원격에 적용하는 배포까지 수행해야 한다. 기존 프로젝트를 사용하는 예외 경로에서는 현재 인증 제공자와 규칙을 먼저 확인하고, 관련 없는 설정을 초기화하거나 끄지 않는다.

## 별도 설정 저장소에서 실행 시 읽기

- 설정값의 기준은 해당 Apps Script 프로젝트의 스크립트 속성 한 곳이다. HTML·서버 코드·정적 설정 파일에 동일한 값을 고정해 두거나, 속성 조회 실패 시 오래된 하드코딩 값으로 연결하지 않는다. 속성 갱신 시 관련 없는 기존 속성을 지우지 않는다.
- 웹앱을 열 때 기존 1회성 초기 준비 호출에 설정 조회를 포함한다. 서버가 `PropertiesService.getScriptProperties().getProperty()`로 전용 키를 읽고 JSON 구조·필수 공개 설정을 확인한 뒤, SDK에 필요한 공개 필드만 브라우저에 반환한다. 스크립트 속성 전체를 반환하지 않으며 교사 비밀번호·인증 토큰·관리 자격 증명은 포함하지 않는다.
- 브라우저는 받은 설정으로 Firebase App과 인증·RTDB를 초기화한다. 설정이 없거나 잘못되면 디자인된 오류 안내를 표시하고 연결을 중단한다. 값을 추측하거나 이전 프로젝트로 조용히 연결하지 않는다.
- 설정값만 변경한 경우 **다음 웹앱 접속·새로고침 또는 명시적인 ‘다시 연결’ 동작**에서 새 값을 읽는다. 설정 로딩 코드가 배포되어 있다면 값 변경만을 위해 Apps Script 코드를 수정·재배포하지 않는다. 열린 화면의 설정을 바꾸려고 주기적으로 조회하지 않는다.
- 재연결을 제공한다면 이전 리스너를 해제하고 변경된 설정에 맞춰 Firebase App·인증 상태를 다시 준비한다. 이전 프로젝트의 참조·UID·권한 정보를 새 프로젝트에 그대로 사용하지 않는다. 새 인증과 앱의 접근 권한 준비 후 리스너를 연결한다.
- 설정을 읽는 초기 서버 호출은 RTDB 데이터 중계가 아니다. 이후 순수 실시간 상태는 브라우저가 직접 처리한다.
- 설정값 변경으로 새 Firebase 프로젝트의 리소스·익명 인증·보안 규칙·권한 연결까지 자동으로 갖춰지는 것은 아니다. 대상이 바뀌면 필요한 Firebase 설정도 AI가 별도로 적용한다. “재배포 불필요”는 이미 구현된 로더의 연결 설정값 변경에 적용하며 기능·코드 변경에는 기존 배포 절차를 따른다.

## 웹앱에서 익명 인증 사용

- Apps Script HTML Service에서 동작하는 방식으로 Firebase SDK를 로드하고, 실행 시 스크립트 속성에서 읽은 공개 설정으로 초기화한다. 기존 인증 상태가 복원되는 것을 확인한 뒤 필요한 경우 `signInAnonymously()`로 인증한다. 매 새로고침·클릭마다 새 익명 계정을 만드는 흐름은 사용하지 않는다.
- Firebase 익명 인증 후 각 화면의 데이터 작업을 시작한다. 학생 화면은 명렬 확인 뒤 활동으로 이동하고, 교사 화면은 [교사 화면 접근 방식](teacher-access.md)에 따라 곧바로 열거나 화면 진입용 비밀번호 통과 후 연다. 교사 화면의 리스너 시작 시점도 그 UI 흐름에 맞추되, 비밀번호를 Firebase 읽기 권한 조건으로 사용하지 않는다. 별도 교사 신원 확인·교사 권한 발급을 추가하지 않는다.
- 학생에게 Firebase용 별도 로그인 화면이나 Google·이메일 로그인을 추가하지 않는다. 명렬 기반 학번·이름 입력 화면은 기존 기본값대로 유지한다.
- Firebase UID는 익명 계정의 식별자다. 학번·교사 권한을 자동으로 증명하는 값으로 취급하지 않는다. 다른 기기나 초기화된 브라우저에서 같은 UID가 유지된다고 가정하지 않는다.
- `onValue()` 등 공식 리스너를 사용하고, 대상 학급·활동 변경이나 화면 종료 시 기존 리스너를 해제한다. 폴링은 사용하지 않는다.

## 앱에 맞는 Realtime Database 규칙 작성

인터뷰에서 확인한 실시간 반영 데이터·공유 범위·수정 주체로 RTDB 경로와 권한을 설계하고 완성된 JSON을 `database.rules.json` 같은 실제 파일에 작성한다. 보관용 최종 기록의 저장소는 시트이며, 이를 RTDB 전용 영구 기록 구조로 바꾸지 않는다. 질문은 누가 무엇을 볼 수 있고 수정할 수 있는지에 한정하고, 교사에게 JSON이나 경로를 설계하도록 요구하지 않는다.

- 루트 `.read`와 `.write`를 모두 `false`로 두고 필요한 하위 경로에서만 권한을 허용한다. RTDB의 상위 경로 허용은 하위 경로에 적용되므로, 상위에 넓은 권한을 열고 하위에서 막을 수 있다고 가정하지 않는다.
- **읽기:** 화면 반영에 필요한 활동 데이터의 하위 경로는 `auth != null`인 익명 인증 사용자에게 읽기를 허용한다. 교사 화면에만 표시하는 데이터도 Firebase에서는 비밀번호 확인 없이 읽을 수 있는 구성이다. 화면별 표시 범위와 실제 데이터 읽기 권한을 구분하고, 비밀번호로 데이터 비밀을 보호한다고 설명하지 않는다. 명렬 전체·비밀번호·불필요한 과거 기록은 공개 대상에 넣지 않는다.
- **쓰기:** 학생 기록은 `auth.uid` 기반 소유권으로 생성·수정·삭제를 제한한다. UID별 경로나 불변 `ownerUid`를 사용한다. 생성 시 본인 소유임을 확인하고, 수정·삭제 시 기존 기록의 소유자가 요청자와 일치해야 한다. 수정 후에도 소유자가 바뀌지 못하게 한다. 다른 학생의 ID·학번을 보내거나 기존 기록의 소유자 필드를 바꿔 덮어쓰는 요청을 허용하지 않는다.
- 학번·이름의 명렬 대조는 서버에서 수행한다. UID와 학생·학급의 연결을 권한 근거로 사용할 때는 서버가 Firebase 인증 정보를 검증하고 확인 결과를 신뢰할 수 있는 경로로 기록해야 한다. 브라우저가 보낸 UID·학번·반·역할 값을 그대로 승인하거나 자신에게 권한을 등록하게 하지 않는다.
- **교사 권한 발급 없음:** 화면용 비밀번호 확인 결과를 Firebase 교사 역할·권한표·커스텀 클레임으로 연결하지 않는다. 교사 역할용 관리 API·권한 발급 서버를 추가하지 않는다. URL 매개변수·브라우저의 역할 값·화면 진입 상태를 타인 기록의 쓰기 허용 조건으로 사용하지 않는다.
- 교사가 제어하는 활동 진행 상태와 학생별 기록 경로를 분리한다. 활동 진행 기능 때문에 공통 부모 경로의 쓰기를 열어 학생 기록의 소유권 제한을 무력화하지 않는다. 학생 기록을 관리 목적으로 수정·삭제하는 기능이 별도로 요구되면 가능한 처리 방식과 범위를 따로 정하며, 화면용 비밀번호만으로 데이터 관리 권한이 확보된 것으로 처리하지 않는다.
- `.validate`로 필수 필드, 허용 필드, 자료형, 길이·값의 범위와 변경할 수 없는 소유자 정보를 검증한다. 삭제에는 `.validate`가 적용되지 않으므로 삭제 권한은 `.write` 조건에서 별도로 처리한다. 생성·수정·삭제 모두 실제 기능에 맞게 허용하거나 거부한다.
- 코드가 접근하는 경로·조회 범위와 규칙을 맞춘다. 문법 오류나 권한 오류를 해결하기 위해 규칙을 전체 공개로 바꾸지 않는다.

익명 인증과 UID 소유권은 실제 학생·교사 신원을 증명하지 않는다. 교사 화면용 비밀번호와 데이터 소유권 제한은 서로 다른 기능이다. 교사 역할을 발급하지 않아도 학생 기록의 소유권 검사·입력값 검증·삭제 권한 검사는 유지한다.

## 실제 배포와 사용자 점검으로 연결

1. 앱의 활동 데이터 읽기 범위·학생 기록 소유권·데이터 검증에 맞는 규칙 파일을 작성한다. 화면 진입용 비밀번호와 Firebase 교사 권한 발급을 연결하지 않는다. AI가 에뮬레이터나 별도 규칙 검증 도구를 실행하는 절차는 추가하지 않는다.
2. 작성한 파일을 대상 프로젝트와 인스턴스에 배포한다. MCP의 배포 도구나 다음과 같이 대상을 지정한 CLI를 사용한다. 실제 사용 중인 버전에서 명령과 구성을 지원하는지 확인한다.

   ```text
   npx -y firebase-tools@latest deploy --only auth,database --project PROJECT_ID
   ```

3. 배포 작업이 비동기이면 작업 완료 결과를 확인한다. 배포 명령이 반환한 오류는 수정하되, 이를 계기로 별도 테스트를 실행하지 않는다. 성공 응답은 배포 성공의 근거로만 사용한다.
4. 완료 보고에는 실제 프로젝트·앱·DB, 익명 인증 설정, 규칙 파일과 배포 결과를 기록한다. 웹앱의 인증·허용된 동작·화면 간 실시간 반영은 사용자가 확인할 체크리스트로 제공한다. 상태는 구현·배포 결과와 사용자 점검 전 또는 사용자가 알려준 점검 결과로 구분한다.

도구·권한·실행 환경 때문에 자동 처리가 막히면 실패한 단계와 필요한 조치를 안내하고, 가능한 코드·규칙 준비는 계속한다. 사용자에게 수동 복사를 일괄 요구하거나, 실패를 성공으로 보고하거나, 실패한 설정을 그대로 반복 실행하지 않는다.
