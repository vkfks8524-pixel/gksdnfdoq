# 시트 저장·실시간 반영·중복과 충돌 처리

모든 앱의 데이터 구조와 저장·수정·삭제를 구현할 때 적용한다. 이 역할 분담과 처리 원칙은 기본값이며, 교사에게 기술 선택 질문으로 반복하지 않는다. 화면의 저장 버튼과 동작을 설명하고 README에도 반영한다.

## 저장소의 역할

| 저장소 | 기본 역할 |
| --- | --- |
| Google Sheets | 보관할 최종 입력값·응답·답안·활동 내용·결과와 이후 조회·수정에 필요한 기준 데이터 |
| Firebase Realtime Database | 다른 화면에 바로 보여줄 현재 활동 상태와 최소한의 임시 표시 데이터·변경 정보 |

- 시트가 저장 기록의 기준이다. RTDB에만 최종 결과를 남기고 “저장 완료”라고 표시하지 않는다. Firebase를 사용하지 않는 앱도 동일한 시트 저장 규칙을 적용한다.
- RTDB에는 현재 화면을 갱신하는 데 필요한 최소 정보만 둔다. 최종 응답 일부를 실시간 화면에 표시해야 한다면 현재 활동용 복사본으로 사용할 수 있으나, 보관할 원본은 시트에 저장한다. 명렬 전체나 과거 활동 기록을 실시간 반영 목적 없이 복제하지 않는다.
- 시트 기록을 복사한 RTDB 표시 데이터가 시트의 최종 기록과 다르면 시트를 기준으로 복구한다. 오래된 실시간 값으로 시트를 역으로 덮어쓰지 않는다. 시트에 보관하지 않는 순수 활동 상태에는 비교할 시트 원본이 없어도 된다.
- 활동 종료·새 활동 시작 등 명시적인 버튼에서 해당 활동의 임시 상태를 정리할 수 있다. 보관할 기록의 시트 저장을 마친 뒤 해당 활동 범위만 정리하며, 이 정리가 시트의 기존 기록 삭제로 이어지지 않게 한다.

## 데이터 변경은 명시적인 버튼으로

- 저장·제출·수정 적용·삭제·활동 종료 등 명확한 버튼이 변경 작업의 출발점이다. 시트 기록은 Apps Script 서버에서 처리하고, 시트에 보관하지 않는 상태는 브라우저에서 RTDB로 직접 전송한다. 입력 중, 포커스 이탈, 페이지 종료, 타이머, Firebase 리스너만으로 시트에 자동 저장·수정·삭제하지 않는다.
- 시트의 추가 조회도 “불러오기”, “최신 내용 확인” 같은 버튼으로 실행한다. 웹앱을 열 때 필요한 연결·스키마·최초 데이터 준비와, 사용자가 요청한 로그인에 필요한 서버 조회는 허용한다. 폴링은 하지 않는다.
- 버튼으로 확정한 변경에 따른 RTDB 갱신은 같은 작업의 일부다. 사용자에게 시트 저장 버튼과 Firebase 반영 버튼을 매번 따로 누르게 하지 않는다. 활동 시작·다음 문제 등 실시간 상태만 바꾸는 동작도 명시적인 버튼으로 실행한다.
- 다른 화면은 Firebase 리스너로 변경 내용을 자동 수신·표시한다. 받는 화면에 확인 버튼을 추가로 요구하지 않는다. 이 리스너에서 시트를 반복 조회하거나 같은 기록을 다시 저장하지 않는다.
- 시트의 중복 요청 판단·잠금·충돌 감지는 Apps Script 서버에서, RTDB 전용 상태의 충돌 처리는 Firebase의 규칙·트랜잭션 등으로 처리한다. 교사에게 이를 위한 별도 기술 버튼이나 설정을 요구하지 않는다.

## 시트에 보관할 기록의 저장·수정·삭제

1. 버튼을 누르면 작업 식별자, 안정적인 기록 식별자, 변경 내용과 수정 대상의 기준 버전 등을 서버에 보낸다. 서버는 입력값과 기록 소유권 등 필요한 변경 권한을 검사한다. 학생 요청의 학번·기록 ID만 믿지 않고 확인된 학생 정보와 기존 기록을 대조해 다른 학생의 기록을 수정·삭제하지 못하게 한다. 교사 화면 진입용 비밀번호나 브라우저의 역할 값은 이 검사의 대체 수단이 아니다.
2. 스크립트 잠금을 얻은 뒤 해당 작업이 이미 처리됐는지와 대상 기록의 최신 상태를 읽는다. 행 번호만으로 대상을 식별하지 않는다. 행 추가·정렬·삭제 후에도 같은 기록을 찾을 수 있는 ID를 사용한다.
3. 처리한 동일 요청이면 기존 처리 결과를 반환한다. 새 요청이면 버전과 변경 가능 조건을 확인한 뒤 시트에 반영하고, 재시도 때 결과를 찾을 수 있는 처리 정보를 남긴다.
4. 필요한 시트 변경을 반영한 뒤 잠금을 해제한다. 성공·실패 모두에서 잠금과 스피너가 정리되게 한다. 시트 작업에서는 잠금 해제 전에 `SpreadsheetApp.flush()`로 대기 중인 변경을 반영한다.
5. 시트에 반영한 값과 버전을 기준으로 필요한 RTDB 화면 반영을 수행하고, 저장 결과와 실시간 반영 결과를 구분해 화면에 전달한다.

이 순서는 시트에 보관할 기록에 적용한다. 최종 활동 내용의 저장이 필요한 “종료”·“제출” 버튼도 시트 저장을 포함한다.

## RTDB만 사용하는 상태의 직접 동기화

- 현재 문제 번호·활동 진행 상태처럼 시트에 보관하지 않는 값은 **브라우저 → Firebase Web SDK → RTDB → 다른 화면의 리스너**로 처리한다. 이 상태의 읽기·쓰기마다 `google.script.run`, Apps Script의 외부 요청 또는 별도 중계 서버를 거치게 하지 않는다.
- 앱 시작의 설정 조회·명렬 대조·선택한 교사 화면 진입용 비밀번호 확인은 별도 초기 준비다. 이후 실시간 상태는 Firebase 익명 인증과 RTDB 규칙으로 직접 처리한다. 필요한 활동 데이터 읽기를 허용하되 학생 기록 쓰기는 본인 소유에 제한하며, 별도의 Firebase 교사 권한 발급은 추가하지 않는다. 직접 통신을 위해 쓰기를 전체 공개로 바꾸지 않는다.
- 명시적인 버튼에서 `set()`·`update()` 등으로 변경하고, 수신 화면은 `onValue()` 등으로 자동 반영한다. 전송 경로가 직접 통신이라는 이유로 입력 중 자동 저장이나 폴링을 추가하지 않는다.
- 같은 공유 값을 동시에 바꾸는 경우 필요한 `runTransaction()`과 버전 비교를 사용한다. 여러 경로를 함께 바꿔야 할 때는 원자적 갱신을 사용하고, 같은 작업 재시도는 같은 ID로 식별해 중복 증가·중복 생성되지 않게 한다. RTDB 상태의 동시 변경을 직렬화하려고 Apps Script 잠금을 추가하지 않는다.
- 트랜잭션 콜백은 재실행될 수 있으므로 그 안에서 시트 기록·외부 호출 등의 부수 효과를 실행하지 않는다. 사용자 초안과 충돌 안내는 실제 반영 결과에 맞춰 처리한다.
- 순수 상태 변경 성공을 시트의 영구 저장 완료로 표시하지 않는다. 이후 보관이 필요한 제출·종료 버튼에서는 위의 시트 저장 흐름을 적용한다.

## 시트의 중복 저장 방지

- 처리 중 버튼을 비활성화하는 것과 별개로 서버에서도 같은 작업을 한 번만 반영한다. 응답 지연이나 연결 끊김 후 같은 요청을 다시 보내도 새 행이 추가되지 않게 한다.
- 같은 작업을 재시도할 때는 같은 요청 ID를 사용한다. 이미 처리한 ID로 다른 내용이 들어오면 새 변경으로 조용히 적용하지 않는다.
- 저장한 요청·기록 ID와 처리 결과를 시트의 필요한 열 또는 작업 기록에 남겨 실행이 끝난 뒤에도 판단할 수 있게 한다. 브라우저 변수나 일시적인 캐시만으로 처리 여부를 판단하지 않는다.
- “학생별로 활동당 하나의 최종 응답”인 앱은 활동·학생 등으로 기록을 식별한다. 재제출은 같은 기록의 수정으로 다룬다. 여러 기록을 쌓는 앱은 새로운 기록과 이전 작업 재시도를 구분한다. 기술적인 중복 방지를 이유로 사용자가 의도한 여러 기록까지 합치지 않는다.
- 삭제 작업도 재시도 결과를 식별할 수 있게 한다. 이미 삭제된 기록을 다시 삭제했다는 이유로 다른 행을 삭제하거나, 오래된 저장 요청으로 기록을 되살리지 않는다.

## 시트 동시 수정과 시트·RTDB 일부 실패

- `LockService.getScriptLock()` 등으로 실제 시트 데이터 변경 구간을 보호한다. 시트·헤더 초기화뿐 아니라 시트 기록의 중복 판단과 변경에도 적용한다. 잠금을 얻지 못했으면 성공으로 처리하지 않고 다시 시도할 수 있게 안내한다.
- 잠금만으로 오래된 화면의 덮어쓰기를 막았다고 가정하지 않는다. 수정·삭제 시 사용자가 보고 있던 버전과 현재 기록의 버전을 비교한다. 불일치하면 입력 내용을 보존하고 커스텀 안내와 “최신 내용 확인” 버튼을 제공한다. 사용자가 확인·수정 후 다시 명시적으로 저장하게 한다.
- 시트 직접 편집은 앱의 스크립트 잠금을 따르지 않는다. 직접 편집을 허용한 데이터는 현재 값 비교 등으로 이를 고려하고, 모든 동시 변경을 잠금 하나로 통제한다고 설명하지 않는다.
- 시트 저장이 실패하면 최종 저장 성공을 알리거나 RTDB에 확정 결과를 먼저 공개하지 않는다. 시트 기록은 남았는데 응답만 실패한 경우도 재시도 시 기록·요청 ID로 구분한다.
- 시트 저장 성공 후 RTDB 반영만 실패했다면 “저장은 완료됐지만 다른 화면 반영을 다시 시도해야 합니다”처럼 안내한다. 재시도 버튼은 저장한 결과의 반영만 다시 수행하며 시트에 같은 기록을 추가하지 않는다.
- 여러 요청의 RTDB 반영 순서가 뒤바뀌어도 최신 상태가 오래된 상태로 바뀌지 않도록 버전 순서를 반영한다. 오래된 수정·삭제 재시도가 새 기록이나 새 버전을 덮어쓰지 않게 한다.
- 시트와 RTDB가 한 번에 원자적으로 저장된다고 가정하지 않는다. 처리한 단계와 결과를 구분하고, 사용자가 누른 재시도·불러오기 버튼에서 일관된 상태로 이어갈 수 있게 구현한다. 자동 폴링·주기적 재저장으로 해결하지 않는다.

## 사용자 점검과 설명서

AI는 직접 중복 제출·동시 수정 테스트를 하지 않는다. [배포와 사용자 점검 안내](delivery-and-checklist.md)에 따라 사용자에게 같은 버튼의 재시도로 기록이 중복되지 않는지, 두 화면에서 같은 기록을 수정하면 충돌을 안내하는지, 최종 결과가 시트에 남고 RTDB의 임시 정보와 구분되는지 확인할 항목을 제공한다. README에는 실제 저장 버튼·수정·삭제 순서와 저장 성공/동기화 실패 시 사용자가 할 일을 쉽게 설명한다.
