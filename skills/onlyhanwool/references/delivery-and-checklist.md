# 구현 완료 후 배포와 사용자 점검 안내

이 앱의 작업 분담은 **AI가 코드 작성·설정·README 갱신·푸시·배포를 수행하고, 사용자가 점검·검증을 수행하는 것**이다. 기존 지침의 AI 직접 동작 테스트·에뮬레이터·규칙 검증 절차는 이 방식으로 대체한다.

## 실제 구현에서 배포로 이어가기

- 인터뷰에서 핵심 흐름을 만들 정보가 모이면 실제로 사용할 수 있는 MVP를 먼저 구현·배포한다. 사용자에게는 “먼저 사용해볼 첫 버전”으로 설명하고, 화면별 링크를 보며 피드백하도록 한다. MVP에도 데이터 저장·중복과 충돌 처리·접근 방식·공통 UI·README를 적용한다.
- 합의한 기능·사용 흐름·디자인을 실제 `.gs`·`.html` 등 프로젝트 파일에 구현한다. 채팅에 코드만 출력하는 것으로 대신하지 않는다.
- 앱 전체에서 불필요한 외부 서비스·라이브러리를 추가하지 않는다. Apps Script·Google Sheets·브라우저 기본 기능과 사용자가 선택한 Firebase SDK로 필요한 기능을 구현할 수 있으면 이를 우선한다. 합의한 기능에 추가 의존성이 실제로 필요하면 그 목적과 필요한 설정을 설명하고 해당 범위에만 사용한다. 이 원칙을 선택한 Firebase 연동이나 필요한 기능을 생략하는 이유로 삼지 않는다.
- 최초 구현부터 웹앱 프로젝트 루트에 `README.md`를 작성하고, 이후 코드나 기능을 바꾸는 같은 작업에서 관련 설명과 변경 이력을 함께 갱신한다. 기존 README의 유효한 설명은 보존하고, 변경되거나 없어진 기능의 오래된 설명은 수정·제거한다.
- 기존 코드·설정·자료를 보존하고 필요한 부분을 수정한다. 현재 `.clasp.json`의 대상과 `rootDir`, 업로드 대상 파일을 파악해 다른 앱을 덮어쓰지 않는다. Firebase 로컬 설정·관리 자격 증명 등 Apps Script 실행에 필요 없는 파일은 업로드 대상에 넣지 않는다.
- Git 저장소를 사용하는 프로젝트는 기존 브랜치·변경사항·원격 연결과 작업 방식을 확인해 그 방식에 맞게 변경사항을 관리한다. 사용자의 기존 변경을 보존하며, **별도 요청 없이 다른 원격 저장소로 푸시하지 않는다.** 원격 저장소를 임의로 추가·변경하거나 새 저장소를 만들어 공개하지 않는다. Apps Script에 대한 `clasp push`·배포와 Git 원격 푸시를 구분하며, 앱 배포 요청을 다른 Git 저장소로의 업로드 요청으로 해석하지 않는다.
- 코딩이 끝나면 앱 테스트를 추가 단계로 실행하지 않고 푸시·배포를 진행한다. AI가 브라우저에서 링크를 열어보거나, 테스트용 응답을 쓰거나, 단위·통합 테스트·린트·에뮬레이터·별도 보안 규칙 검증을 실행하지 않는다.
- 파일·설정 읽기, 배포 대상 식별, 도구 버전·사용법 확인, 실행 결과 확인은 구현·배포를 위한 작업이다. 푸시·배포 명령 자체가 보고한 오류는 읽고 수정한다. 성공하지 않은 명령을 완료로 보고하지 않는다.
- 앱 내부의 입력값 검사·학생 명렬 확인·교사 비밀번호 대조·Firebase 인증 및 Rules의 데이터 검증은 구현한다. 이것은 AI가 앱 동작을 시험하는 것과 구분한다.

## clasp 푸시와 기존 주소를 유지하는 배포

1. 현재 도구의 도움말과 기존 프로젝트 메타데이터로 사용 중인 `clasp` 명령, 배포 ID·URL·버전을 파악한다. 배포가 여러 개라면 사용자가 제공한 기존 URL과 연결된 배포를 우선한다. 대상을 구분할 근거가 없을 때만 필요한 식별 정보를 확인한다.
2. 실제 `clasp push`를 실행하고 종료 결과를 확인한다. 파일이 업로드됐다는 사실과 웹앱의 배포 버전이 바뀌었다는 사실을 구분한다.
3. 기존 웹앱 배포가 있으면 새 코드 버전을 만들고 **그 배포 ID가 새 버전을 사용하도록 업데이트**한다. 기존 배포를 삭제하거나 새 배포로 교체하지 않으며 접속 URL을 유지한다. 해당 `clasp` 버전이 지원하는 기존 배포 업데이트 명령과 옵션을 사용한다.
4. 기존 웹앱 배포가 없는 경우에만 신규 웹앱 배포를 만든다. 코드·버전만 저장하고 배포 완료로 보고하지 않는다.
5. 명령/API 결과에서 실제 배포 ID·버전·실행 URL을 확보한다. 기존 배포 업데이트 권한이 없거나 실패하면 원인과 필요한 조치를 안내하며, 주소가 바뀌는 신규 배포로 조용히 우회하지 않는다.

기존 배포의 실행 사용자·접근 대상 설정은 앱의 합의된 이용 방식에 맞춰 유지한다. 설정 변경이 실제로 필요한 경우에만 그에 맞게 처리한다. Google 권한 승인이 필요한 단계는 사용자에게 안내한다.

## 화면별 클릭 가능한 링크 제공

- 확인된 실제 배포 실행 URL을 기준으로, 코드에 구현한 모든 화면 분기의 링크를 제공한다. 교사·학생·결과 화면처럼 화면 이름을 링크 제목에 사용한다.
- 예를 들어 구현한 분기가 `page=teacher`, `page=student`이면 실제 배포 URL에 각각 해당 매개변수를 붙인다. 기존 쿼리 매개변수가 있으면 URL 처리를 통해 올바르게 결합한다.
- 링크는 사용자가 바로 클릭할 수 있는 Markdown으로 제공한다. 코드 블록 안의 주소, 임의로 만든 배포 ID, 아직 배포되지 않은 주소를 실제 접속 링크처럼 제시하지 않는다.
- 버전이 고정된 배포의 실행 URL을 제공한다. 개발용 주소를 일반 배포 주소로 혼동하지 않는다.
- 사용자에게 전달할 링크를 확인한다는 이유로 AI가 웹앱에 접속해 동작을 시험하지 않는다. 배포 결과에서 얻은 주소와 코드의 분기를 조합해 제공한다.

## 앱에 맞는 사용자 점검 체크리스트

배포 링크 다음에 사용자가 할 동작과 기대 결과를 한 문장씩 적은 체크박스 목록을 제공한다. 아래 항목 중 실제 앱에 해당하는 것만 골라 화면·버튼·데이터 이름을 구체적으로 바꾼다. 관련 없는 Firebase·비밀번호·학생 화면 점검은 제외한다.

- [ ] 각 화면의 접속 링크를 열면 해당 화면이 표시되는지 확인합니다.
- [ ] 처음 열 때 필요한 탭·헤더가 생성되고, 다시 열면 중복 생성되거나 기존 값이 바뀌지 않는지 확인합니다.
- [ ] 실제 명렬에 있는 학번·이름은 통과하고, 틀리거나 서로 다른 행의 조합은 통과하지 않는지 확인합니다.
- [ ] 교사용 URL 기본 접근이면 바로 교사 화면이 열리고, 명렬에 있는 학년·반이 드롭다운에 표시되는지 확인합니다.
- [ ] 화면 진입용 비밀번호를 선택했다면 첫 화면이 비밀번호 입력이고, `설정!A1`과 일치할 때만 교사 화면으로 이동하는지 확인합니다.
- [ ] 핵심 입력·저장·조회·수정·삭제 동작이 의도한 결과를 만들며 기존 기록을 잘못 바꾸지 않는지 확인합니다.
- [ ] 서로 다른 학생으로 접속했을 때 자신의 기록만 수정·삭제할 수 있고, 다른 학생의 기록은 변경할 수 없는지 확인합니다. Firebase 임시 기록과 시트의 최종 기록에 각각 적용합니다.
- [ ] 최종 입력값과 활동 내용이 시트에 남고, 저장·수정·삭제가 해당 버튼을 눌렀을 때 실행되는지 확인합니다.
- [ ] 같은 저장 요청을 재시도해도 같은 기록이 중복 생성되지 않는지 확인합니다.
- [ ] 두 화면에서 같은 기록을 열어 먼저 한쪽에서 수정한 뒤 다른 쪽에서 저장하면, 기존 수정을 덮어쓰지 않고 최신 내용을 확인하도록 안내하는지 확인합니다.
- [ ] 안내·오류·확인창이 앱 디자인에 맞게 나타나고, 취소를 누르면 해당 변경이 실행되지 않는지 확인합니다.
- [ ] 작업 중 스피너와 상황에 맞는 문구가 나타나고, 연속 클릭으로 중복 처리되지 않으며, 성공·실패 후 스피너가 사라지는지 확인합니다.
- [ ] 실시간 반영을 선택했다면 두 화면을 열어 제출한 내용이 정한 대상 화면에 새로고침 없이 나타나는지 확인합니다. 실시간 연결 중 스피너가 계속 남지 않는지도 확인합니다.
- [ ] 시트에 보관하지 않는 활동 상태를 바꾸는 버튼이 있다면 다른 화면에 바로 반영되고, 해당 동작만으로 시트 기록이 추가되지 않는지 확인합니다.
- [ ] Firebase 연결 설정을 변경한 작업이라면 새로고침 또는 앱에 제공된 ‘다시 연결’ 동작으로 변경한 대상에 연결되는지 확인합니다. 점검만을 위해 운영 설정을 임의로 바꾸지는 않습니다.
- [ ] 버튼 조회를 선택했다면 해당 버튼을 눌렀을 때 최신 내용이 나타나는지 확인합니다.
- [ ] 학생·교사 화면에서 인터뷰로 정한 정보와 기능만 제공되는지 확인합니다.
- [ ] 사용할 휴대폰·태블릿·컴퓨터에서 글씨·버튼·배치가 편한지 확인합니다.
- [ ] 기존 배포가 있었다면 이전에 사용하던 주소로 새 버전이 열리는지 확인합니다.

새 구조 생성이나 삭제 기능을 확인하기 위해 실제 자료를 지우도록 안내하지 않는다. 필요한 경우 테스트용 복사본이나 사용자가 준비한 시험용 기록을 사용하도록 한다. 앱을 처음 만들 때 비어 있는 명렬·비밀번호 설정은 점검 전에 준비할 항목으로 설명한다.

결과 공유는 “어느 화면에서 어떤 버튼을 눌렀는지, 기대한 결과와 실제 결과가 무엇인지” 정도면 충분하도록 안내한다. MVP를 본 사용자의 기능·배치·사용 순서에 관한 피드백도 받아, 필요한 질문만 이어가며 다음 수정을 구체화한다. 해당 부분과 README를 함께 수정하고 같은 주소로 다시 배포한 뒤 변경된 부분의 점검 항목을 제공한다. 이때도 AI가 직접 동작 테스트를 실행하지 않는다.

## 교사용 README.md 작성과 갱신

README는 프로그래밍을 전혀 모르는 교사가 혼자 읽고 준비·사용·관리를 따라 할 수 있는 **상세한 한국어 사용 설명서**다. 개발자를 위한 기술 개요나 간단한 기능 목록으로 대신하지 않는다. 아래 내용 중 해당 앱에 필요한 것을 포함한다.

| 내용 | 작성할 사항 |
| --- | --- |
| 앱 소개 | 어떤 수업·업무에 쓰는지, 누가 사용하는지, 핵심 기능과 전체 사용 흐름 |
| 바로 접속하기 | 실제 교사·학생·결과 화면 링크와 각 링크를 누구에게 전달할지 |
| 처음 준비하기 | 사용할 시트와 접속 방법, 자동 연결·탭 생성 설명, 실제로 필요한 권한 승인이나 초기 연결 단계, 명렬·비밀번호 등 사용자가 채울 내용 |
| 화면별 사용법 | 화면에 보이는 정확한 버튼·입력란 이름, 입력 예시, 누르는 순서, 처리 후 나타날 결과, 수정·삭제·취소 방법 |
| 시트 관리 | 생성되는 각 탭과 열의 의미, 최종 입력값·활동 기록의 저장 위치, 저장·수정·삭제 버튼과 재시도 방법, 교사가 입력·수정할 항목, 기존 기록을 보존하는 관리 방법 |
| Firebase 안내 — 사용하는 앱만 | RTDB는 현재 화면의 실시간 반영용이고 보관할 기록은 시트에 저장된다는 역할 구분, AI가 설정한 부분과 사용자에게 남은 조치, 연결 설정은 별도 스크립트 속성에서 시작 시 읽고 값 변경 후 다음 접속·재연결에 적용된다는 설명, 저장 성공 후 동기화만 실패했을 때 할 일 |
| 실제 활용 예시 | 수업 준비 → 학생 활동 → 결과 확인처럼 그 앱의 실제 사용 장면을 따라 하는 예시 |
| 문제 해결 | 로그인 실패, 빈 명렬, 비밀번호 미설정, 권한 안내, 저장·조회 실패, 로딩이 끝나지 않는 상황 등 해당 앱의 문제별 증상과 사용자가 할 일 |
| 유지보수 | 자료 백업 방법, 명렬·설정 변경 방법, 기능 수정을 AI에게 요청하는 방법, 기존 주소로 업데이트된 앱을 사용하는 방법 |
| 사용자 점검 | 현재 앱의 동작과 기대 결과를 담은 점검 체크리스트, 사용자 점검 전인지 사용자가 결과를 알려줬는지에 대한 정확한 상태 |
| 배포 정보와 변경 이력 | 실제 배포 URL·ID·버전·배포 결과, 변경 날짜와 기능 추가·수정·삭제 및 오류 수정 내용 |

### 비전공 교사가 따라 할 수 있게 쓰기

- 행동 순서대로 번호를 매기고 “어느 화면에서 무엇을 누르면 어떤 결과가 나오는지”를 구체적으로 쓴다. 전문 용어가 필요하면 짧게 풀어 설명한다. 개발 도구 설치나 명령어 실행을 교사의 일상 사용 단계에 불필요하게 넣지 않는다.
- 실제 구현된 화면·버튼·기능을 기준으로 작성한다. 코드와 작업 기록으로 알 수 없는 결과를 확인했다고 쓰지 않는다. 존재하지 않는 메뉴·내보내기·백업 버튼 등을 만들어 설명하지 않는다.
- 예시는 실제 학생 정보 대신 가상 값을 사용한다. 교사 비밀번호·학생 명렬 전체·개인 키·인증 토큰은 문서에 기록하지 않는다.
- 학생 로그인은 실제 명렬 구조와 학번 형식에 맞춰 설명한다. 교사 화면 접근은 앱에서 선택한 방식만 설명하고, 화면 진입용 비밀번호를 사용할 때는 `설정!A1`에 값을 입력하는 방법을 안내한다. 비밀번호의 실제 값은 적지 않는다.
- 비밀번호를 쓰는 앱에서는 **교사 화면 진입용이며 Firebase 활동 데이터 자체의 읽기를 제한하지 않는다**는 범위를 설명한다. Firebase 교사 권한 발급은 없고, 필요한 활동 데이터는 익명 인증 사용자가 읽을 수 있으며 학생 기록의 수정·삭제는 본인 소유로 제한된다는 점을 구분한다. 화면용 비밀번호를 데이터 보안 인증으로 표현하지 않는다.
- 시트 연결·탭 생성은 앱이 자동 처리하는 흐름으로 설명한다. 필요한 초기 연결·권한 승인·실제 학생 자료 입력은 자동 처리와 구분한다. 수동으로 탭·헤더를 일일이 만들거나 Firebase SDK 설정을 복사하도록 과거 절차를 다시 넣지 않는다.
- 문서는 이 스킬 파일 없이도 사용할 수 있어야 한다. 교사에게 스킬 내부 참조 문서를 찾아 읽도록 넘기지 않고, 필요한 사용법과 점검 항목을 README 안에 담는다.

### 변경할 때마다 함께 갱신

- 기능 추가·수정·삭제 → 관련 사용법·활용 예시·점검 항목을 갱신한다.
- 화면·버튼·디자인·사용 흐름 변경 → 화면 설명과 누르는 순서를 갱신한다.
- 시트·로그인·비밀번호·Firebase 설정 변경 → 준비 방법·관리 방법·문제 해결을 갱신한다.
- 내부 코드 수정·오류 수정 → 사용 방식이 그대로여도 날짜와 변경 이유를 변경 이력에 기록한다.
- 푸시·배포 완료 → 명령 결과에서 확보한 실제 URL·ID·버전·배포 상태를 반영한다. 예정 버전을 실제 배포 버전처럼 미리 기록하지 않는다. 새 배포가 실패하면 기존 운영 버전과 이번 실패 상태를 구분한다.

README는 로컬 웹앱 프로젝트 또는 그 프로젝트의 Git에서 관리하며, Apps Script 실행 파일로 푸시하지 않는다. 사용법은 코드 수정과 함께 갱신하고, 배포 후 얻은 정보는 마지막으로 반영한다. README의 배포 정보만 고쳤다는 이유로 앱 배포를 반복하지 않는다.

문서를 완성하기 위해 AI가 앱을 직접 테스트하지 않는다. 코드·설정·실행 명령 결과·사용자가 알려준 결과를 근거로 문서를 최신화한다. 필요한 README 갱신이 빠졌다면 작업을 완료한 것으로 보고하지 않는다.

## 완료 보고

보고에는 이번 버전에서 구현한 주요 기능, 푸시·배포의 실제 결과, 유지한 배포 주소 또는 최초 배포 주소, 화면별 링크, 필요한 초기 준비, 사용자 점검 체크리스트, README 작성·갱신 내용과 실제 파일 링크를 포함한다. 첫 버전이면 MVP임을 밝히고 결과물을 보며 정할 후속 항목과 구분한다. 상태는 “MVP 구현·배포·사용 설명서 갱신 완료 / 사용자 동작 점검 전”처럼 표시하며, 하지 않은 검증을 통과했거나 후속 기능까지 완성됐다고 말하지 않는다.

**이번 작업에서 추가·수정·삭제한 파일 목록과 각 파일의 변경 목적도 포함한다.** 서버 코드·화면·Firebase 규칙·설정 파일·README 등 실제로 변경한 파일을 대상으로 하며, 사용자나 이전 작업의 변경을 이번 작업의 성과로 보고하지 않는다. 현재 존재하는 파일은 가능한 환경에서 클릭 가능한 파일 링크로 제공하고, 삭제된 파일은 경로와 삭제 사실을 표시한다. 파일 내용을 그대로 나열하거나 비밀번호·인증 토큰·학생 정보를 보고에 포함하지 않는다.
