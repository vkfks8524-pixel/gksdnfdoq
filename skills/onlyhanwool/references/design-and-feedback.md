# 디자인 인터뷰와 화면 피드백

앱의 사용자·목적·주요 화면이 드러났을 때 디자인을 대화로 정하고, 화면을 구현할 때 이 지침을 적용한다. 기능 인터뷰와 같은 방식으로 한 번에 1~2개만 질문하고, 이미 받은 답은 다시 묻지 않는다.

## 디자인도 인터뷰로 정하기

- 추상적인 디자인 전문 용어 대신 실제 느낌과 사용 장면으로 질문한다. 분위기·색상, 화면 배치, 주로 쓰는 기기, 글자와 버튼의 크기 중 다음 결정에 필요한 것을 고른다.
- 예시를 제시할 때는 항상 자유롭게 설명할 수 있다는 문장을 덧붙인다. “차분하고 깔끔한 느낌, 밝고 친근한 느낌, 활동성이 느껴지는 느낌 중 가까운 것이 있나요? 혹은 원하시는 분위기를 자유롭게 설명해주셔도 좋아요.”처럼 묻는다.
- 색상을 아직 모르면 “선호하는 색이 있나요? 없으면 말씀하신 분위기에 맞춰 제가 제안해드릴 수 있어요. 혹은 참고하고 싶은 화면이나 느낌을 설명해주셔도 좋아요.”처럼 답할 수 있게 돕는다.
- 화면 배치는 기능과 연결한다. 예를 들어 수업 중 전체 응답을 확인하는 앱은 “한 화면에 여러 학생의 응답이 많이 보이는 구성이 편할까요, 한 명씩 크게 보는 구성이 편할까요? 혹은 원하시는 모습을 설명해주셔도 좋아요.”처럼 묻는다.
- 기기·화면 크기·사용 장소가 이미 정해졌다면 재사용한다. 학생용은 터치 조작, 교사용은 학급 전체 정보 확인 등 실제 요구에 맞춰 구체화한다.
- 사용자가 잘 모르거나 AI에게 맡기면 이유를 붙여 적합한 방향을 제안한다. 별도 선호가 없으면 읽기 쉬운 글씨와 충분한 버튼 크기를 갖춘 깔끔한 반응형 화면을 기본으로 안내한다. 선택할 의향이 없는 세부 색상·수치까지 계속 질문하지 않는다.
- 핵심 기능과 디자인 방향으로 MVP를 만들 수 있으면 최신 기획 요약을 바탕으로 제작·배포한다. 세부 색상·간격·배치는 사용자가 실제 결과물을 보며 피드백하도록 하고, 첫 버전 전에 모든 시각적 세부 사항을 질문으로 확정하지 않는다.

## 이모지 없는 시각 디자인 기본값

- 사용자가 이모지를 명시적으로 요청하지 않으면 웹앱 디자인에 이모지를 사용하지 않는다. 제목·버튼·메뉴·카드·상태 표시·알림창·빈 화면·스피너 등 AI가 만드는 UI 전체에 적용한다. “밝게”, “친근하게”, “학생들이 좋아하게” 같은 분위기 요청만으로 이모지를 추가하지 않는다.
- 시각 요소가 필요한 곳에는 SVG 선 아이콘, 원·둥근 사각형·선·구분선 등의 CSS 도형을 사용한다. 선 굵기·모서리·색상·크기를 일관되게 맞추고 충분한 여백으로 정돈된 인상을 만든다. 장식을 과하게 늘리기보다 기능과 정보의 구분을 돕는 형태를 선택한다.
- 간단한 도형은 인라인 SVG나 CSS로 구현한다. 기존에 사용하는 아이콘 도구가 있으면 스타일을 맞춰 활용하되, 장식만을 위해 불필요한 외부 라이브러리를 추가하지 않는다. 아이콘만 있는 조작 요소에는 의미를 알 수 있는 접근 가능한 이름을 제공한다.
- 사용자가 이모지를 직접 요청한 경우에만 요청한 범위에 사용한다. 이 규칙은 AI가 만드는 UI 디자인에 대한 것이며, 학생이 입력한 내용이나 학습자료 속 이모지를 임의로 삭제·변경하는 근거로 삼지 않는다.

## 중간 요약에 남길 내용

디자인에 의미 있는 결정이 생기면 기존 앱 요약에 한두 줄로 반영한다. 사용자가 정한 디자인과 AI가 제안 중인 디자인을 구분한다.

예: “디자인: 밝고 차분한 분위기, 파란색 포인트, 학생 화면은 큰 버튼과 카드 중심, 휴대폰에서도 사용.”

색상이나 배치가 바뀌면 화면뿐 아니라 알림창·버튼·스피너에도 같은 방향을 적용한다. 구현 전 구상을 이미 완성된 화면처럼 표현하지 않는다.

## 디자인된 알림·확인·입력

- 웹앱에서 브라우저 기본 `alert()`, `confirm()`, `prompt()`를 사용하지 않는다. 정보·성공·오류 안내는 화면에 어울리는 토스트나 모달, 결정이 필요한 작업은 커스텀 확인창, 추가 입력은 커스텀 입력창으로 만든다.
- 성공·실패를 색상만으로 구분하지 않고 문구와 필요한 아이콘으로 전달한다. 사용자가 다시 할 수 있는 동작을 분명히 표시한다.
- 확인창의 확인·취소 결과를 실제 처리 흐름에 연결한다. 취소하면 해당 변경을 실행하지 않는다.
- 글씨·버튼 크기와 명암을 읽기 쉽게 하고, 대화상자의 포커스·키보드 조작과 화면 읽기 이름을 제공한다.
- 오류 메시지에 비밀번호·토큰·학생 명렬 전체 등을 포함하지 않는다. 앱에 필요한 안내만 보여준다.

## 디자인된 전역 동적 스피너

- 앱 전체에서 공유하는 로딩 표시를 구현한다. 선택한 디자인과 어울리는 애니메이션·배경·문구를 사용하고, 작업에 따라 “화면을 준비하고 있어요”, “로그인 정보를 확인하고 있어요”, “응답을 저장하고 있어요”처럼 문구를 갱신한다.
- 시작 시 시트 초기화·필요 데이터 불러오기, 로그인, 저장·수정·삭제, 사용자가 누른 조회 등 주요 비동기 처리 동안 표시한다. 처리 중인 버튼의 중복 실행을 막고, 완료하면 다시 사용할 수 있게 한다.
- 성공·실패·예외 등 모든 종료 경로에서 로딩 상태를 정리한다. `google.script.run`은 성공·실패 핸들러를 모두 두고, Promise 흐름은 `finally` 등으로 종료 처리를 빠뜨리지 않는다.
- 동시에 여러 작업이 진행되면 작업 수나 작업 ID로 관리하여, 하나가 끝났다는 이유로 다른 작업의 로딩 표시가 사라지거나 영구히 남지 않게 한다.
- 서버가 주지 않은 진행률을 임의의 퍼센트로 표시하지 않는다. 알 수 있는 작업 단계에 따라 문구를 바꾼다.
- Firebase의 지속적인 실시간 리스너 연결은 로딩 작업으로 계속 계산하지 않는다. 초기 연결·필요한 최초 데이터 수신 등이 끝나면 스피너를 종료하고 이후 업데이트는 화면에 반영한다.
- 앱 사용 중의 동작 점검은 사용자가 수행한다. AI는 이 요소들을 구현하고 [사용자 점검 체크리스트](delivery-and-checklist.md)에 실제 동작과 기대 결과를 넣는다.
