# 교사의 생각을 구체화하는 초기 인터뷰

프로젝트 클론과 파일 확인이 끝난 뒤 읽는다. 목표는 교사가 관심 있는 분야에서 출발해 하고 싶은 활동과 필요한 기능을 말로 풀어내도록 돕고, 함께 만들 앱의 목적과 첫 사용 흐름을 정리하는 것이다.

## 큰 분야에서 구체적인 사용 흐름으로

기본 흐름은 **수업·업무·그 외 → 구체적인 활동이나 업무 → 원하는 목적 → 사용자와 행동 → 우선 기능**이다. 사용자가 이미 설명한 단계는 건너뛴다. 이 흐름 전체를 한 번에 질문하지 않는다.

첫 질문에서 분야를 들은 뒤에는 다음 예시 중 맥락에 맞는 질문을 고르거나 바꿔 쓴다.

| 선택한 분야 | 다음 질문 예시 | 이어서 좁힐 내용 |
| --- | --- | --- |
| 수업 | “학생이 직접 참여하는 활동인가요, 선생님이 수업을 준비하거나 진행할 때 쓰는 도구인가요? 둘 다여도 괜찮아요. 혹은 원하시는 사용 방식을 자유롭게 설명해주셔도 좋아요.” | 학생 참여라면 퀴즈·생각 모으기·학습 기록 등 하고 싶은 활동과 수업에서 기대하는 결과를 살핀다. |
| 업무 | “어떤 업무에 쓰고 싶으세요? 신청을 받는 일, 일정·명단 관리, 자료 정리처럼 말씀해주셔도 돼요. 혹은 다른 업무를 자유롭게 설명해주셔도 좋아요.” | 사용자가 고른 업무에서 누가 무엇을 입력하고 어떤 결과를 확인할지 좁힌다. |
| 그 외 | “어떤 상황에서 누가 쓰는 도구를 생각하고 계세요? 개인 기록, 취미 활동, 모임 운영 같은 예도 괜찮아요. 예시 외에 원하시는 내용을 편하게 설명해주셔도 돼요.” | 사용자가 자유롭게 설명한 목적을 바탕으로 활동과 사용자를 정리한다. |

분야는 대화를 돕는 출발점이다. 수업과 업무가 겹친다고 재분류를 요구하지 않는다. 분야를 고르기 어렵다면 익숙한 활동의 예시를 2~3개 보여주고 관심 가는 장면에서 시작한다. 새로운 활동을 해보고 싶은 이유도 앱의 목적이 될 수 있다.

예시 답변은 현재 질문에 맞춰 제공한다. 분야를 고르는 단계에서 완성된 기능 목록을 제시하거나 여러 단계의 질문을 한꺼번에 묻지 않는다.

수업용 앱의 교사·학생 화면 분리가 정해졌다면 `SKILL.md`의 시작 화면 기본값을 반영한다. 학생의 학번·이름을 명렬의 같은 행과 대조하는 로그인, 교사용 URL로 바로 접속하는 학년·반 드롭다운은 기본 적용 사항이다. 이 항목들을 다시 고르게 하지 않고 그다음 활동을 구체화한다. 교사 화면에 들어가기 전 비밀번호를 거치고 싶다는 요구가 나오면 [교사 화면 접근 방식](teacher-access.md)에 따라 화면 진입용 비밀번호를 학년·반 선택 앞에 둔다. 비밀번호는 화면 진입용이며 Firebase 활동 데이터 읽기 제한이나 교사 권한 발급과 연결하지 않는다. 사용자가 요청한 별도 구성이 있으면 이를 우선한다.

학생의 동작과 그 결과를 볼 화면이 파악되면 [화면 반영 방식 인터뷰](sync-interview.md)에 따라, 다른 화면에 바로 나타날지 확인하는 사람이 버튼을 눌러 가져올지 묻는다. 이때 바로 반영은 Firebase 설정·연결이 필요하고, 버튼으로 확인은 Firebase 연결 없이 가능하다고 각 선택지에 함께 설명한다. 이 선택으로 Firebase 사용 여부를 정한다. 사용자가 이미 반영 방식을 명확히 설명했다면 질문을 반복하지 않고 연결 필요 여부를 포함해 요약한다.

기본 기능과 화면이 드러나면 [디자인 인터뷰](design-and-feedback.md)도 같은 대화 흐름으로 진행한다. 분위기·색상·화면 배치·글자와 버튼 크기를 실제 사용 장면과 연결해 좁히고, 예시 뒤에는 자유로운 설명을 안내한다. 디자인만 별도의 긴 설문으로 한꺼번에 묻지 않는다.

사용자가 웹앱 안에서 AI를 활용하고 싶다고 말한 경우에만 [API 설명과 키 보유 확인](ai-api-interview.md)으로 이어간다. “AI도 사용해볼까요?”를 먼저 묻거나 AI 기능을 기본 예시·추천 목록에 넣지 않는다. 이 조건은 첫 기획 인터뷰뿐 아니라 MVP를 본 뒤의 피드백 대화에도 동일하게 적용한다.

## 답변의 구체성에 맞춰 진행하기

| 답변 상태 | 인터뷰 방식 |
| --- | --- |
| 목적·사용자·기능이 구체적임 | 설명을 짧게 요약하고 빠진 핵심 사항만 묻는다. 다른 앱 예시를 다시 나열하지 않는다. |
| 만들 앱의 이름이나 주제만 있음 | 그 앱을 실제로 쓸 상황을 묻는다. 예를 들어 “독서 기록 앱”이라면 누가 어떤 기록을 남기고 누가 확인할지 구체화한다. |
| 수업·업무·그 외의 분야만 정해짐 | 해당 분야의 활동이나 업무 종류를 예시와 함께 묻고, 그다음 목적과 사용 흐름으로 좁힌다. |
| 사용자가 먼저 불편한 일을 말함 | 그 내용에서 사용 분야와 목적을 파악하고, 필요할 때 현재 처리 방식이나 바라는 변화를 묻는다. |
| 아이디어가 없거나 말하기 어려움 | 먼저 수업·업무·그 외에서 관심 분야를 고르도록 돕는다. 이미 고른 분야가 있다면 그 안에서 관련 예시를 제시한다. |
| 원하는 기능이 많음 | 이루고 싶은 핵심 목적을 요약하고, 먼저 쓸 수 있게 만들 기능과 나중에 더할 기능을 함께 고른다. |

이 분류를 사용자에게 검사표처럼 제시하지 않는다. 답변을 들으며 자연스럽게 방식을 바꾼다.

## 대화의 한 차례를 구성하는 방법

필요에 따라 다음 요소를 조합한다. 매 응답에 모든 요소를 억지로 넣지 않는다.

1. **말을 받아 정리한다.** “학생들이 남긴 내용을 한곳에서 보려는 거군요.”처럼 이미 들은 내용을 짧게 표현한다.
2. **다음 단서를 구체적으로 묻는다.** “학생들이 어떤 내용을 남기는 활동을 생각하고 계세요?”처럼 선택한 분야 안에서 목적을 좁힌다.
3. **말하기 어려우면 방향을 제시한다.** “질문에 대한 생각을 모으기, 배운 내용을 정리하기, 다음 수업에 궁금한 점을 남기기 중 가까운 것이 있나요? 혹은 생각하신 활동을 자유롭게 설명해주셔도 좋아요.”처럼 답할 수 있는 발판을 준다.
4. **답변을 앱의 행동으로 연결한다.** “학생이 한 줄을 남기면 선생님 화면에 모이도록 하는 방식이 도움이 될 것 같아요.”처럼 제안한다. 제안이 사용자의 의도와 맞는지 필요한 경우 확인한다.

동의 여부만 반복해서 묻는 대화가 되지 않게 한다. 이미 명확히 말한 내용은 받아들이고 다음으로 진행한다. 미정인 내용을 사용자 답변인 것처럼 만들지 않는다.

중요한 내용이 모였거나 방향이 달라졌을 때에는 다음 질문에 앞서 아래의 중간 요약을 보여준다. 짧은 답변을 받아 정리하는 것과, 앱 전체의 현재 구상을 보여주는 중간 요약을 함께 활용한다.

## 생각을 끌어내는 질문의 재료

아래 질문을 정해진 순서대로 모두 묻지 않는다. 앞선 답변에서 아직 부족한 단서 하나를 고른다.

| 찾으려는 단서 | 질문 예시 |
| --- | --- |
| 사용 분야 | “수업 관련, 업무 관련, 그 외 중 어디에 가까운가요? 혹은 원하시는 내용을 자유롭게 설명해주셔도 좋아요.” |
| 구체적인 활동·업무 | “어떤 활동에 쓰고 싶으세요? 학생 생각 모으기, 퀴즈, 학습 기록 같은 예도 괜찮아요. 다른 활동을 생각하고 계시면 편하게 말씀해 주세요.” |
| 활동의 목적 | “그 활동을 통해 학생들이 무엇을 해보거나 알게 되면 좋을까요?” |
| 업무의 목적 | “그 업무에서 어떤 정보를 모으거나 결과를 확인할 수 있으면 좋을까요?” |
| 현재 처리 방식 — 사용자가 기존 업무를 언급한 경우 | “지금은 그 일을 어떻게 하고 계세요? 종이, 메신저, 시트 중 쓰시는 방식이 있을까요? 다른 방식이라면 자유롭게 설명해주셔도 좋아요.” |
| 불편한 부분 — 사용자가 불편을 언급한 경우 | “말씀하신 과정에서 특히 바꾸고 싶은 부분은 어디인가요?” |
| 사용자의 구분 | “학생도 직접 입력하나요, 아니면 선생님이 기록해서 보시는 용도인가요? 혹은 생각하신 사용 방식을 편하게 설명해주셔도 좋아요.” |
| 원하는 변화 | “이 앱을 쓰고 나면 어떤 일이 줄어들거나 가능해지면 좋을까요?” |
| 첫 사용 흐름 | “학생이 앱을 열었을 때 처음 무엇을 하면 될까요?” 시작 화면이 이미 정해졌다면 “로그인한 뒤에는 어떤 활동을 하면 될까요?”처럼 그다음 행동을 묻는다. |
| 결과 확인 | “선생님은 입력된 내용을 어떤 모습으로 보면 편할까요?” |
| 우선순위 | “말씀하신 것 중 먼저 하나가 해결된다면 가장 도움이 되는 건 무엇인가요?” |

학년·인원·기기·사용 장소는 답에 따라 앱의 사용 방식이 달라질 때 묻는다. 이미 나온 맥락으로 충분한 항목은 다시 확인하지 않는다. 명렬에서 확인할 수 있는 학년·반 목록을 사용자에게 다시 나열하게 하지 않는다.

## 상황별 대화 예시

### 이미 아이디어가 구체적인 경우

사용자: “학생들이 책 제목과 한 줄 감상을 쓰고, 저는 학생별로 모아보는 독서 기록 앱을 만들고 싶어요.”

AI: “학생이 독서 기록을 남기고 선생님은 학생별로 확인하는 앱이군요. 학생이 작성한 기록을 나중에 수정할 수도 있어야 할까요?”

사용자·입력 내용·교사의 확인 방식은 이미 주어졌으므로 다시 묻지 않는다. 사용자가 수정 가능 여부까지 말했다면 이 질문도 생략한다.

### 수업 분야에서 활동으로 좁히는 경우

사용자: “수업에 쓸 거예요.”

AI: “학생들이 직접 참여하는 활동인가요, 선생님이 수업을 준비하거나 진행할 때 쓰는 도구인가요? 혹은 원하시는 사용 방식을 자유롭게 설명해주셔도 좋아요.”

사용자: “학생들이 직접 참여했으면 해요.”

AI: “어떤 활동을 해보고 싶으세요? 퀴즈 풀기, 각자의 생각 모으기, 배운 내용 기록하기처럼요. 예시 외에 해보고 싶은 활동을 자유롭게 설명해주셔도 좋아요.”

사용자: “각자의 생각을 모아보고 싶어요.”

AI: “학생들이 질문에 자기 생각을 남기는 활동이군요. 모인 생각은 선생님만 확인하나요, 학생들도 서로 읽고 이야기하면 좋을까요? 혹은 다른 활용 방법을 생각하셨다면 편하게 말씀해 주세요.”

학생의 행동과 결과를 좁혀가되, 사용자가 아직 말하지 않은 실시간 표시·점수·순위 등을 확정하지 않는다.

### 업무 분야에서 사용 흐름으로 좁히는 경우

사용자: “업무에 쓰려고요.”

AI: “어떤 업무에 쓰고 싶으세요? 신청을 받는 일, 일정·명단 관리, 자료 정리 같은 예도 괜찮아요. 혹은 다른 업무를 자유롭게 설명해주셔도 좋아요.”

사용자: “방과후 프로그램 신청을 받고 싶어요.”

AI: “프로그램 신청을 받는 앱이군요. 신청은 학생, 학부모, 담당 선생님 중 누가 입력하나요? 혹은 생각하신 신청 방식을 자유롭게 설명해주셔도 좋아요.”

사용자가 업무 이름만으로 분야를 이미 설명했다면 앞의 분야 선택 단계는 건너뛴다.

### 주제만 말한 경우

사용자: “수업 참여를 높이는 앱이요.”

AI: “어떤 참여 활동을 생각하고 계세요? 질문에 자기 생각 남기기, 퀴즈 풀기, 모둠 의견 모으기 중 가까운 것이 있나요? 예시 외에 생각하신 활동을 편하게 설명해주셔도 좋아요.”

아직 말하지 않은 경쟁, 점수, 순위 기능을 먼저 확정하지 않는다. 참여가 필요한 실제 장면을 찾는다.

### 불편은 있지만 앱이 떠오르지 않는 경우

사용자: “과제 확인이 너무 번거로워요.”

AI: “과제를 확인할 때 어떤 부분이 특히 번거로우세요? 제출 여부를 표시하는 일, 안 낸 학생을 찾는 일, 학생에게 다시 알려주는 일처럼요. 혹은 다른 상황을 자유롭게 설명해주셔도 좋아요.”

사용자: “안 낸 학생을 찾아서 적는 게 귀찮아요.”

AI: “제출 표시를 하면 아직 안 낸 학생이 자동으로 모여 보이는 방식이 도움이 될 것 같아요. 제출 표시는 선생님이 하시나요, 학생이 직접 하나요? 혹은 원하시는 처리 방식을 자유롭게 설명해주셔도 좋아요.”

### 계속 ‘잘 모르겠어요’라고 하는 경우

같은 추상적인 질문을 반복하지 않는다. 앞서 선택한 분야나 말한 맥락에서 가능한 방향을 2~3개로 좁히고, 각각 실제로 어떻게 쓰는지 한 문장으로 설명한다. 분야도 정하기 어렵다면 수업·업무·그 외 각각의 간단한 예시로 관심 있는 방향부터 찾는다.

추천은 이유와 함께 제시하고 사용자가 바꾸거나 다른 방향을 말할 수 있게 한다. 사용자가 답을 못 했거나 시간이 지났다는 이유로 동의한 것으로 간주하지 않는다.

## 대화 중 유지할 기획 메모

답변에서 알게 된 내용을 다음 항목으로 정리해 재사용한다. 이 메모를 바탕으로 다음 절의 중간 요약을 사용자에게 보여준다. 매 답변마다 메모 전체를 출력하거나 별도 파일을 만들 필요는 없다.

- 사용 분야와 앱으로 이루고 싶은 목적
- 사용자와 사용하는 상황
- 선택한 활동·업무와, 사용자가 설명한 경우의 현재 처리 방식이나 불편한 부분
- 사용자의 행동에서 결과 확인까지 이어지는 핵심 흐름
- 교사용 URL로 바로 접근하는 기본값 또는 선택한 화면 진입용 비밀번호 사용 여부, 그에 따른 첫 화면과 통과 후 흐름. Firebase 교사 권한을 발급하지 않는다는 기준과 학생 기록 소유권 제한은 유지하며, 비밀번호 실제 값은 기록하지 않는다.
- 먼저 구현하고 싶은 기능, 나중에 검토할 기능
- 사용자가 웹앱 내 AI 기능을 요청한 경우에만: AI가 할 일, 선택한 서비스, API 설명 여부, 키 보유 여부와 다음 준비 단계. 키 문자열은 메모에 남기지 않으며 사용자가 보유했다고 답한 것과 실제 연결 완료를 구분한다.
- 이번 MVP에서 실제로 사용할 핵심 흐름, 사용자 피드백으로 정할 후속 항목, 현재 버전에 대한 사용자 의견
- 디자인 분위기·색상·배치·사용 기기와 글자·버튼 크기에 관한 결정 및 제안
- 화면 간 공유할 데이터와 대상 화면, 자동 반영·버튼 조회 여부, 그에 따른 Firebase 사용 여부
- Firebase 사용 시 관리 도구·로그인·대상 프로젝트 준비 상태와 필요한 연결 조치, 새 웹앱의 새 프로젝트 기본값 및 실제 생성 여부, 익명 인증 설정과 규칙 배포 상태. 앱 동작은 사용자 점검 결과와 구분한다.
- 조건에 따라 기본 적용한 구성과 사용자가 변경한 기본값
- 아직 결정하지 않은 내용과 AI가 제안한 가정

사용자가 한 말을 근거로 확정된 내용과 제안을 구분한다. 스킬의 기본값으로 적용한 사항은 별도로 기록하며, 사용자가 직접 선택한 것처럼 표현하지 않는다. 대화 방향이 바뀌면 메모도 갱신한다. 기능을 취소하거나 바꾸면 그 기능에 연결된 화면, 사용 흐름, 다음 질문도 함께 검토해 수정한다. 이전에 취소한 기능을 다음 요약에서 다시 확정된 기능처럼 제시하지 않는다.

## 인터뷰 중간에 현재 웹앱 구상 보여주기

사용자가 인터뷰가 끝나기 전에도 어떤 웹앱이 구상되고 있는지 확인할 수 있도록, 현재까지의 내용을 짧은 요약으로 주기적으로 보여준다. 대화의 질문·답변을 시간순으로 나열하기보다 지금 만들려는 앱의 모습을 설명한다.

### 요약을 보여줄 시점

- 처음으로 앱의 용도와 핵심 활동이 잡혔을 때 첫 요약을 보여준다. 아직 모르는 내용은 미정으로 남긴다.
- 그 뒤에는 의미 있는 답변이 몇 차례 쌓이거나, 주요 사용자·화면·기능·사용 흐름이 구체화됐을 때 갱신한다. 보통 2~3번의 의미 있는 답변을 참고하되, 고정된 횟수를 채울 필요는 없다.
- 사용자가 기존 방향을 바꾸거나 중요한 기능을 추가·삭제하면 바로 요약을 갱신한다.
- 사용자가 현재까지의 정리를 요청하면 그 시점의 내용으로 즉시 보여준다.
- 앱 구상에 변화가 없는 짧은 대화에서는 같은 요약을 반복하지 않는다. 매 질문마다 전체 계획을 길게 출력하지 않는다.

### 요약에 담을 내용

“현재까지 구상한 웹앱”처럼 알아보기 쉬운 문구로 시작하고, 대체로 4~6개의 짧은 항목이나 작은 표로 작성한다. 내용이 적으면 더 짧게 한다.

- **한 줄 소개:** 누구를 위해 무엇을 하는 앱인지 설명한다. 이름을 아직 정하지 않았다면 이름 대신 기능으로 표현한다.
- **정해진 내용:** 사용자가 명확히 말한 목적, 사용자, 주요 기능, 필요한 화면 중 현재 중요한 것을 정리한다.
- **기본 적용:** 스킬에 설정된 기본값 중 이번 앱의 조건에 맞아 적용한 내용을 보여준다. 사용자가 직접 선택한 내용이나 아직 동의하지 않은 AI 제안과 구분한다. 적용한 기본값이 없으면 생략한다.
- **사용 흐름:** 누가 어떤 행동을 하고 어떤 결과를 보는지 자연어 또는 짧은 화살표 순서로 보여준다. 정해진 부분까지만 연결한다.
- **디자인:** 분위기·색상·배치·주요 기기에 관한 결정이 생기면 한두 줄로 정리한다. 미정인 디자인을 사용자 결정으로 표현하지 않는다.
- **반영 방식:** 다른 화면에 자동으로 나타나는지 버튼을 눌러 확인하는지, 어떤 데이터를 누가 보는지 정리하고 Firebase 사용 여부를 함께 표시한다. Firebase 연결을 준비하는 중이면 도구·로그인·대상 프로젝트의 확인 상태와 필요한 조치도 짧게 덧붙인다. 앱에 해당하는 경우 사용 흐름 항목에 합쳐 설명해도 된다.
- **제안 중인 내용:** AI가 제안했으나 사용자가 아직 선택하지 않은 내용이 있으면 별도로 표시한다. 제안이 없다면 이 항목은 생략한다.
- **아직 정할 내용:** 다음 설계에 영향을 주는 핵심 미정 사항만 적는다. 아직 이야기하지 않은 세부 기술 항목을 길게 나열하지 않는다.
- **이번에 달라진 점:** 이전 요약에서 중요한 변경이 있을 때 한 문장으로 표시한다. 필요하면 다른 항목과 합쳐 간결하게 작성한다.

모든 항목을 채우려고 화면이나 기능을 만들어 넣지 않는다. 기획 중인 내용을 이미 구현한 기능처럼 표현하지 않는다. 중간 요약은 사용자의 결정을 확인할 수 있게 하는 설명이며, 전체 개발·배포에 대한 새 승인 절차로 취급하지 않는다.

### 요약 뒤에 대화 이어가기

“제가 이해한 내용 중 다르거나 바꾸고 싶은 부분이 있으면 편하게 말씀해 주세요.”처럼 수정할 수 있음을 안내한다. 매번 별도 승인 답변을 기다릴 필요는 없으며, 이어서 가장 필요한 질문 1~2개를 한다. 질문에 선택지나 예시가 있으면 자유롭게 설명할 수 있다는 안내도 끝에 덧붙인다.

사용자가 정정하면 이를 우선 반영한 뒤 관련 질문을 이어간다. 내용이 서로 충돌해 방향을 정할 수 없을 때만 그 부분을 구체적으로 확인한다. 사용자가 다음 질문에 답했다고 해서, 요약에 남겨둔 미정 사항이나 AI 제안까지 모두 동의한 것으로 간주하지 않는다.

### 중간 요약 예시

아래는 사용자가 “교사가 질문을 올리면 학생이 한 줄로 자기 생각을 남기고, 학생끼리 서로 읽는 활동을 하고 싶다”고 설명한 경우의 예다. 교사용·학생용 화면 분리는 AI가 제안한 상태이며, 다른 화면에 반영하는 시점도 아직 정하지 않았다고 가정한다.

> **현재까지 구상한 웹앱**
>
> - **만들 앱:** 수업 중 학생들의 생각을 모으고 함께 읽는 앱
> - **정해진 내용:** 선생님이 질문을 올리고, 학생이 한 줄로 답변을 남기며, 학생들도 서로의 답변을 읽을 수 있음
> - **사용 흐름:** 선생님이 질문 제시 → 학생이 답변 작성 → 서로의 생각 읽기
> - **제안 중:** 질문을 올리는 교사용 화면과 답변을 쓰는 학생용 화면을 나누는 구성
> - **아직 정할 내용:** 다른 화면에 자동으로 반영할지 버튼으로 확인할지, 이름 표시 여부
>
> 제가 이해한 내용 중 다르거나 바꾸고 싶은 부분이 있으면 편하게 말씀해 주세요.
>
> 학생이 답변을 제출하면 다른 학생 화면에는 어떤 방식으로 나타나면 좋을까요?
>
> 1. **바로 반영 — Firebase 연결 필요:** 새로고침 없이 답변이 바로 나타나며, Firebase 설정·연결 과정이 필요해요.
> 2. **버튼으로 확인 — Firebase 연결 없이 가능:** 각자 ‘답변 불러오기’를 눌렀을 때 최신 답변을 가져와요.
>
> 혹은 원하시는 방식을 자유롭게 설명해주셔도 좋아요.

이후 사용자가 “답변은 선생님만 볼 수 있게 해주세요”라고 바꾸면, 정해진 내용과 사용 흐름 모두를 교사만 답변을 확인하는 구성으로 갱신하고 “이번에 달라진 점: 학생끼리 답변을 읽는 기능을 제외했습니다”라고 알려준다. 이 정정만으로 다른 미정 사항이나 화면 분리 제안이 확정되지는 않는다.

### 수업용 앱의 화면 분리가 정해진 뒤 요약하는 예시

위 대화에서 사용자가 “수업용이고, 교사 화면과 학생 화면은 나눠주세요”라고 정했다면 기존 화면 분리 제안을 정해진 내용으로 옮기고, 조건에 맞는 기본 시작 화면을 추가한다.

> - **정해진 내용:** 수업용 앱이며 교사 화면과 학생 화면을 분리
> - **학생 화면 기본 적용:** 학번과 이름으로 로그인하며, `명렬` 탭의 같은 행에서 두 값이 모두 일치하면 학생 활동 화면으로 이동
> - **교사 화면 기본 적용:** 교사용 URL로 접속하면 교사 기능을 사용할 수 있으며, 명렬의 5자리 학번에서 구성한 학년·반 드롭다운으로 시작
>
> 시작 방식은 이렇게 기본 구성하겠습니다. 원하시는 방식이 다르면 편하게 말씀해 주세요.

이 예시는 전체 요약 중 화면 구성에 관한 항목만 발췌한 것이다. 기존에 정해진 앱의 목적과 핵심 활동도 함께 유지한다. 이 기본값을 사용하는 경우 학생 로그인 입력 항목, 명렬 대조 기준, 학년·반 목록의 출처를 미정으로 표시하거나 다시 질문하지 않는다. 이후 사용자가 화면 진입용 비밀번호를 선택하면 교사 흐름을 “교사용 URL → 비밀번호 입력 → 설정 탭 A1과 일치하면 학년·반 선택”으로 갱신한다.

## MVP 제작을 시작할 기준

누가, 어떤 상황에서, 무엇을 입력·실행하고, 누가 어떤 결과를 보는지 설명할 수 있어 **핵심 흐름 하나를 실제로 사용할 수 있는 첫 버전**을 만들 수 있으면 제작으로 넘어간다. 화면별 세부 기능을 모두 확정하거나 정해진 질문 수를 채우려고 인터뷰를 늘리지 않는다.

- 핵심 화면과 입력·저장·결과 확인, 공유 범위와 접근 방식, 자동 반영 여부를 사용자 답변과 이미 정한 기본값으로 구성할 수 있으면 된다. 보관 데이터는 시트, RTDB는 실시간 반영이라는 기본값을 다시 선택하게 하지 않는다.
- 디자인은 구현 가능한 방향이 있으면 충분하다. 세부 색상·간격·필터·다운로드 등 첫 사용에 꼭 필요하지 않은 사항은 결과물을 보며 보완한다. 사용자가 AI에게 맡긴 부분은 이유를 붙여 정하고 요약에 표시한다.
- 핵심 활동이나 공개 범위처럼 답이 없으면 앱의 의미가 달라지는 내용은 필요한 만큼만 확인한다. 학생 자료·접근 권한 등 실제 실행에 필요한 준비는 누락된 상태를 설명하고 이어간다.
- MVP에도 기존 데이터 보존, 버튼 기반 저장, 중복·충돌 처리, 정한 로그인·권한, 커스텀 알림·스피너, 실제 배포와 README를 적용한다. 가짜 데이터 화면이나 저장되지 않는 화면을 완성된 첫 버전으로 전달하지 않는다.

제작 전에 현재 목적·사용자·핵심 흐름·첫 버전의 기능과 디자인을 짧게 요약하고, 후속 피드백으로 정할 항목을 분리한다. 이미 합의한 내용을 다시 승인받는 절차를 추가하지 않는다. 실제 파일 구현 후 [배포와 사용자 점검 안내](delivery-and-checklist.md)에 따라 링크와 체크리스트를 제공한다. 최초 버전은 “먼저 사용해볼 첫 버전”으로 안내한다.

## 결과물을 보며 완성하기

사용자가 접속 링크와 체크리스트로 직접 사용한 뒤 피드백하면, 해당 화면·버튼·사용 장면을 기준으로 다음 수정을 정한다. 예: “직접 사용해보니 바꾸고 싶은 부분이 있나요? 버튼 위치, 입력 순서, 결과를 보는 방식 같은 내용도 좋아요. 혹은 느끼신 점을 자유롭게 설명해주셔도 좋아요.”

추상적인 전체 요구사항 인터뷰를 처음부터 다시 시작하지 않는다. 한 번에 1~2개의 필요한 후속 질문으로 문제나 선호를 구체화하고, 바뀔 내용을 요약한 뒤 구현한다. README와 변경 이력을 갱신하고 같은 배포 주소로 업데이트하며, 바뀐 부분에 맞는 사용자 점검 항목을 제공한다. AI는 사용자를 대신해 앱을 테스트하지 않는다.
